# Local offer relay prototype

## Hosted testnet offer preview

The separate Cloudflare Workers/D1 offer preview is deployed at https://hegemon-swap-testnet.willdoyle422.workers.dev. It supports offers, reservations and encrypted browser messages using the API below. A connected Ethereum wallet can perform a read-only Sepolia escrow check against independently agreed terms. It compares chain ID, genesis, pinned runtime code, asset and escrow state at a confirmed snapshot and current head, with at least ten minutes remaining. A Bitcoin testnet4 check reconstructs the agreed P2WSH script in the browser and compares it with two-confirmation, unspent output data from a fixed Blockstream service, via the Worker. It requires at least six blocks before refund. A Cardano preview check compares the output to the pinned Aiken validator address, exact datum bytes, ADA and native-token bundle, using the Koios indexer through the Worker. It requires two confirmations and ten minutes before expiry. Check that the browser address matches the compiled Aiken source with `PYTHONPATH=scripts:/workspace/chain-tools/public-test-python python3 scripts/check_cardano_preview_address.py`. These intervals are test thresholds, not a complete cross-chain timeout policy. These checks trust their providers and the code served by the site. The hosted page hides local-node controls; it does not execute, monitor or recover swaps. The operator supplying browser code can replace it or substitute keys, so participants must authenticate counterparties and must not send wallet keys or swap preimages to the service. A testnet label does not restrict the kinds of offers a visitor can type.

The Worker source and schema are `swap-service/cloudflare/worker.mjs` and `swap-service/cloudflare/schema.sql`. `swap-service/cloudflare/wrangler.jsonc` binds the dedicated `hegemon-swap-testnet` D1 database (ID `bc34dcb0-7983-4413-98c9-a08ba6dce311`). The database was created for this preview; do not execute destructive changes without a backup. Apply the idempotent schema with `node /workspace/chain-tools/cloudflare-cli/node_modules/wrangler/bin/wrangler.js d1 execute hegemon-swap-testnet --remote --config swap-service/cloudflare/wrangler.jsonc --file swap-service/cloudflare/schema.sql`, then deploy with the same executable and `deploy --config swap-service/cloudflare/wrangler.jsonc`. The D1 binding is account-specific. `node --test swap-service/cloudflare/worker.test.mjs` checks the hosted API with an in-memory SQLite adapter; `wrangler dev --local` checks it in the Workers runtime. Do not assume a successful deployment proves real wallet execution.

For a selected offer, the hosted preview can capture the independently supplied Ethereum, Bitcoin or Cardano terms for each side, match the offer's exact assets and common hashlock, and rerun both public-network checks. The two results are separate snapshots. The comparison does not authenticate participants, establish safe relative deadlines or finality, or authorize a claim. Hegemon public-testnet verification is not yet available.

### Hegemon node access

The offer relay itself does not need a Hegemon node. Hegemon wallets do need chain data and a way to submit actions; users could use a trusted shared node rather than running one each. The hosted page does not yet provide that wallet integration. A shared public-facing service would need a deliberately scoped, authenticated or otherwise abuse-controlled gateway; do not expose the full unsafe wallet RPC to the internet. A node or provider learns connection and wallet activity metadata, and its reported chain state is a trust assumption.

The release lists `hegemon.pauli.group:30333` as a P2P seed, and https://hegemon.pauli.group/explorer/ is a read-only explorer. Neither establishes that a public wallet RPC is available. For an existing trusted node, the v0.11.2 guide keeps wallet RPC on loopback and recommends an authenticated private tunnel. After the node operator has provided and authorized such a tunnel, check its loopback endpoint without a wallet or transaction:

    PYTHONPATH=scripts python3 scripts/probe_hegemon_testnet.py --rpc http://127.0.0.1:19944

The check compares the pinned genesis, chain ID, manifest and private-spend relation, lists missing wallet methods and reports the node's claimed health. It never calls `hegemon_submitAction`. It does not authenticate the tunnel, independently verify consensus or replace the wallet's authority and chain-data checks. The RPC port above is an example; the tunnel must already exist and the node operator must authorize access.

The hosted page also has manual Sepolia escrow deployment, token approval/funding, ERC-1155 approval revocation and refund actions through an Ethereum browser wallet. The connected wallet must control the refund address, and the code checks Sepolia chain ID and genesis before requesting each transaction. Each request is recorded in the browser action journal before the wallet prompt; a lost response is uncertain and must be checked in wallet history before retrying. Token deployment and funding are separate transactions. ERC-1155 approval covers all IDs in the token contract until revoked. Use the encrypted secret backup panel and preserve the complete agreed terms separately. These single-leg operations do not check the other leg, implement claims or coordinate a swap. Network snapshots, token issuer behavior and the code supplied by the site are trust assumptions. The 20-minute deployment threshold is a test choice, not a safe cross-chain deadline policy.

Reservations are claimed by an atomic database update and messages are bound to the active reservation. A per-IP, per-minute request budget reduces accidental load but does not prevent distributed abuse. Cloudflare supplies the IP address; the Worker stores a time-windowed hash rather than the raw address. Opportunistic cleanup removes old quota entries and messages and offers seven days after offer expiry. There is no guarantee cleanup runs while the service is idle. Monitor D1 usage and Cloudflare billing/limits; the free tier and access availability can change. Avoid including sensitive information in offers.

This is a local, noncustodial offer directory and opaque message relay. It has no wallet, keys, on-chain validation, matching engine, or swap execution. Offers and reservation credentials do not authorize any transaction. Clients must verify all chain data, maintain their own recovery records, and never send private keys or hashlock preimages to this service.

Run with Node.js 24 or later from the repository root:

    SWAP_DB=/private/path/offers.sqlite SWAP_PORT=8787 node swap-service/server.ts

The default listener is `127.0.0.1:8787`. Keep the SQLite file private. Use `node --test swap-service/server.test.mjs` for the local HTTP and restart tests. The relay is a prototype without public-deployment hardening, authentication of wallet identities, transport security, spam controls or production operational procedures.

## HTTP API

All endpoints return JSON and refuse request bodies over 16 KiB. Times are Unix seconds. `POST /offers` takes exactly `visibility` (`public` or `private`), `expires`, `give`, and `receive`. Each asset object has exactly `chain`, `kind`, `id`, and decimal integer string `amount`. Supported chain/kind pairs are `ethereum` with `eth`, `erc20`, `erc721` or `erc1155`; `cardano` with `ada` or `native`; `bitcoin` with `btc`; and `hegemon` with `hgn`. For ERC-20, the ID is its 0x-prefixed 20-byte address; for ERC-721 and ERC-1155 it is `address:decimal-token-id`; for Cardano native tokens it is `policy-id.asset-name`, both hexadecimal, with a 28-byte policy ID and zero to 32 asset-name bytes. Native coins use an empty ID. ERC-721 quantity is one. The relay checks syntax only; clients must authenticate asset identities and rules on chain. Offers expire between one minute and seven days after creation. The response contains an unpredictable `id` and `ownerToken`; store the owner token privately.

`GET /offers` lists at most 100 live public offers. `GET /offers/{id}` retrieves an offer when its random ID is known; possession of that ID is the private offer link capability, not authentication of a counterparty. New offers may include an uncompressed P-256 `ownerPublicKey` for encrypted conversation setup. `POST /offers/{id}/reserve` acquires one exclusive reservation until the earlier of 24 hours and offer expiry. It returns a confidential `reservationToken` and a separate non-secret `reservationId`; repeated reservations conflict until the existing reservation expires. The active reservation ID is also returned with the offer. An expired reservation's messages are discarded before a new participant joins.

Both owner and current reserver may use `Authorization: Bearer <token>` with `POST /offers/{id}/messages` and body `{"ciphertext":"<base64>","reservationId":"<id>"}` for new inbox-enabled offers, or `{"ciphertext":"<base64>"}` for older offers without an inbox key. The relay atomically checks the active reservation ID before accepting an inbox-enabled message, preventing a stale session from sending to a later reservation. Use `GET /offers/{id}/messages?after=<id>` to read. The relay cannot verify whether payloads are actually encrypted. The local browser board uses AES-256-GCM and binds ciphertext to the offer ID. Anyone with a shared link can impersonate a participant; verify identities separately. A malicious server that serves modified client code can steal the key, so this prototype does not protect against a hostile service operator. Never transmit wallet keys or hashlock preimages. Clients must persist messages they need for recovery. The relay stores at most 100 messages per reservation. `POST /offers/{id}/close` requires the owner token and prevents new reservations; it does not affect on-chain escrows. Message posting requires an unexpired offer, and the reserver can read messages until its reservation expires. The owner can still read retained messages after offer expiry. A reservation or server availability is never proof of funding or of exclusive ownership of an asset.

The relay also serves the local offer board at `http://127.0.0.1:8787/`. Wallet connections are read-only until a user explicitly requests an experimental local action described below. The board does not coordinate or execute complete swaps. Wallet support varies by extension and network. Owner and reservation credentials are stored in browser local storage; clearing it loses access to those relay controls. These credentials are not wallet keys. Private offer links contain the unguessable offer ID and message key and must be shared only with the intended counterparty. A viewer can reserve a new public offer and establish an encrypted conversation without receiving that link. The taker encrypts a fresh session key to the owner's P-256 public key using ephemeral ECDH, HKDF-SHA-256 and AES-GCM, bound to the offer and reservation. The owner's non-extractable private inbox key stays in that browser's IndexedDB; clearing it loses the ability to establish new conversations for that offer. The session key is held in browser local storage. Both participants can compare the displayed full SHA-256 inbox and reservation-key fingerprints over a separate trusted channel; the owner's browser also rejects a changed inbox key it previously saved for that offer. Matching fingerprints alone do not prove wallet identity. Older offers without an inbox key still require their shared link. Neither mode authenticates wallet identities; a malicious relay can substitute inbox keys or serve modified JavaScript, so verify counterparties independently. Localhost links work only on the same machine.

Run `node --test swap-ui/crypto.test.mjs swap-service/server.test.mjs` to check ciphertext authentication and the relay API. To run the two-session browser test from the repository root, install its development-only dependency with `npm ci --prefix swap-service`, install Chromium, and run `node --test swap-service/browser.test.mjs`. Set `CHROMIUM_PATH` if Chromium is not at `/usr/bin/chromium`.

The board also contains a read-only local Ethereum escrow verification form. It checks the exact pinned contract runtime and agreed fields, unspent state and holdings at both a two-confirmation snapshot and the current head through the connected browser provider. It accepts local chain ID 31337 only. The provider can lie or the chain can reorganize; a successful check also cannot prevent token issuer restrictions. Verification itself does not create, sign, or submit an escrow. Verify the reference terms independently.

Rebuild both Ethereum contracts using the pinned Foundry/solc versions before testing. From the repository root run `python3 scripts/export_token_escrow_template.py --check` and the same command with `--native --check` to confirm the bundled runtime templates match the compiled source. `python3 scripts/check_ethereum_escrow_verifier.py --output /workspace/new-verifier-run` tests native ETH and each token kind against fresh local contracts. `node --test swap-service/browser.test.mjs` also exercises the form against a real local Anvil node; it requires the Anvil executable and the development-only Chromium dependency described above.

## Local companion

`scripts/local_swap_companion.py` is a separate process that binds only `127.0.0.1:8788`; it is read-only unless Bitcoin, Cardano or Hegemon actions are explicitly enabled. It can check configured Bitcoin regtest and isolated Cardano nodes, and it can ask the local `private-spend` wallet to verify Hegemon terms. It accepts requests only from the configured local web origin with a random pairing token, and supports no arbitrary commands or client-selected paths. The UI sends the token directly to the companion and holds it only in page memory; it does not send it to the offer relay. A malicious local service that serves altered UI code could still steal the pairing token, and same-user processes are not isolated from each other.

Create a new private directory and start the companion from a local terminal, substituting the paths and ports of the already running isolated test nodes:

    mkdir -m 700 /private/new-companion-dir
    python3 scripts/local_swap_companion.py --token-file /private/new-companion-dir/token \
      --bitcoin-rpc http://127.0.0.1:18443 --bitcoin-cookie /private/bitcoin/regtest/.cookie \
      --cardano-socket /private/cardano/node.socket --cardano-network-dir /private/cardano

Either chain's pair of options can be omitted. For a Hegemon wallet, add `--hegemon-wallet /private/wallet.store --hegemon-manifest /private/manifest.json --hegemon-genesis HEX --hegemon-rpc http://127.0.0.1:9944`. All four Hegemon options are required together. Hegemon verification is available only from an interactive local terminal, on a peerless Development node with the configured genesis. The companion displays the request for local approval and asks for the wallet passphrase in that terminal for each verification. It briefly holds the passphrase in process memory and passes it to `private-spend` over a pseudo-terminal; the browser and offer relay do not receive it. The wallet command reveals only a verification result, position and heights, not the decrypted note opening.

To enable experimental Bitcoin actions, add `--enable-bitcoin-actions --bitcoin-wallet WALLET_NAME --bitcoin-genesis HEX` with the regtest RPC and cookie options. The named Bitcoin Core descriptor wallet must already be loaded and must already contain the exact HTLC descriptor and the participant's private branch key. Import private descriptors locally using a secure Bitcoin Core wallet workflow; do not put private keys in the board, relay, command history or a shared link. The policy is `wsh(or_i(and_v(v:sha256(HASH),pk(CLAIM_KEY)),and_v(v:after(HEIGHT),pk(REFUND_KEY))))`. Before funding, the companion asks the wallet to sign a synthetic refund that is never broadcast, rejecting a wallet that cannot sign the refund branch. Funding, claim and refund require separate terminal approvals. If the wallet is encrypted and locked, its passphrase is entered in that terminal; the companion requests a short unlock and then attempts to relock it. The claim preimage is entered there or unlocked from a startup-configured `--bitcoin-preimage-backup /private/backup.json`; it is passed to the local Bitcoin wallet before broadcast and becomes public on submission. Claim and refund use a fixed 500 satoshi fee for this local test, not fee estimation. Each submission returns an unconfirmed transaction ID. If the response is lost, check wallet history before retrying. These actions do not verify the other leg or implement an atomic swap.

To enable experimental Cardano actions, add `--enable-cardano-actions --cardano-node-pid PID --cardano-genesis SHELLEY_GENESIS_SHA256 --cardano-signing-key /private/payment.skey --cardano-journal-dir /private/cardano-journal` together with the Cardano socket and network directory options. The journal directory must already exist and be user-owned mode 0700. Before submitting, the companion durably creates a private record containing the transaction ID, public action terms and genesis, but no preimage or signing key. Its state is deliberately `prepared_or_submitted`: after interruption, check the chain for that ID before retrying. Keep a separate backup; this is not a complete recovery record. The signing key must be a user-owned mode-0600 file; standard `cardano-cli` payment signing key files are not encrypted by this interface. It derives the enterprise payment address and signer hash from that key. Funding inputs, or the fee and ADA-only collateral inputs for a spend, must already belong to that address; use local Cardano tooling to identify them. The expiry must align with a local slot. The companion checks the node process owns the configured socket, uses the expected loopback configuration and peerless topology, matches the pinned local genesis and validator, and has no established TCP peers at the checks. It validates the exact ADA and native-asset bundle and requires terminal approval. An optional `--cardano-preimage-backup /private/backup.json` unlocks the preimage with a terminal passphrase; otherwise it is typed in the terminal. Building a claim can expose that preimage to the local node before submission. The transaction ID returned is unconfirmed; check its inclusion and confirmation depth independently. This local CLI path is not a CIP-30 transaction interface and does not coordinate a swap.

Open the board at `http://127.0.0.1:8787/`, read the pairing token from the mode-0600 token file locally, and enter it into the board's companion field. The token is a local capability, not a wallet password; do not share it. The default allowed origin is exactly `http://127.0.0.1:8787`. The UI currently expects the companion on port 8788. Cardano verification checks the validator, datum and exact asset value at a node tip; its confirmation depth remains unknown. Bitcoin requires two regtest confirmations. Hegemon defaults to two confirmations and two remaining blocks. These short local thresholds are not public-chain safety margins. Each verifier trusts its local node and requires independently authenticated expected terms.

`PYTHONPATH=scripts python3 -m unittest scripts/test_local_swap_companion.py` checks private pairing-token file handling and exact Cardano decimal conversion. The local pairing scripts exercise the Bitcoin and Cardano companion endpoints against actual fresh nodes; their output directories contain disposable keys and pairing tokens and must remain private.

For experimental manual Hegemon actions, create a separate user-owned mode-0700 handoff directory and add `--enable-hegemon-actions --hegemon-handoff-dir /private/handoffs` to the Hegemon companion invocation. Every typed action is displayed for explicit approval in the companion terminal. Wallet and encrypted handoff passphrases, and claim preimages, are entered there and are not sent by the browser. Preparing an action and submitting it are separate requests. Lock preparation creates an encrypted refund handoff in the specified directory; back it up and protect its separate passphrase. If a response is lost, the wallet may still have submitted or reserved funds: check wallet status before retrying. Submission acknowledgements contain a 32-byte preparation attempt ID and a different 48-byte action ID, and do not establish confirmation. These local actions do not verify the other leg or enforce safe cross-chain deadlines. Preimages become public when a claim is submitted and can remain public even after a reorganization.

Alternatively, save a browser-exported encrypted preimage backup as a user-owned mode-0600 JSON file and start the action companion with `--hegemon-preimage-backup /private/backup.json`. A claim then asks for the backup passphrase in the local terminal and decrypts the saved preimage locally instead of asking the user to type it. The backup file is selected only at companion startup, never by a browser request. This optional path requires Python's `cryptography` package. It has an interoperability test against the actual browser export and has been exercised in a fresh local Hegemon claim. Python and its cryptography library may retain temporary secret copies in process memory. The backup stores only the preimage, not the wallet, handoff or complete swap record.

For experimental Ethereum transactions, start the companion with `--ethereum-rpc http://127.0.0.1:8545` pointed at an already running, non-forked Anvil node. After pairing, the board exposes a deployment form. It compares the connected wallet's chain ID, genesis and head to this trusted local node before requesting wallet approval. Native ETH is funded at deployment. A token escrow is initially unfunded: after the deployment receipt, enter its address with the same agreed terms, submit a separate token approval, confirm its receipt, then submit funding and verify the funded escrow. The form checks the source-pinned code, exact terms and local state before approval or funding, and simulates the requested call. ERC-1155's operator approval covers all IDs in that token contract, not just the offered ID; use the separate revoke button and check its receipt after funding. Record each transaction ID and check its receipt; a lost response is ambiguous and must not be retried without checking wallet history. This is limited to local Anvil and is not a complete swap. Token issuers and nonstandard token behavior can still prevent transfers.

After expiry, the same form can submit a refund from the original refund address. It checks the pinned code and agreed terms, funded/unspent state, chain identity and timestamp, then simulates the refund before requesting wallet approval. To claim before expiry, select a local encrypted secret backup and enter its passphrase. The form checks the preimage hash, source-pinned escrow and funded state at a confirmed snapshot and current head before requesting the claimant wallet's approval. **The preimage is sent to the wallet as soon as it receives the approval request, even if the user declines; a submitted claim makes it public.** The form does not verify the other swap leg or its deadlines. Check both independently before making a claim. Check the transaction receipt and confirmations. Cross-chain coordination and complete recovery are not yet implemented.

The local deadline watch saves a label, chain, genesis hash, deadline and warning threshold in browser storage, and polls the connected local provider while the page is open. Its values are block heights for Bitcoin and Hegemon, Unix seconds for Ethereum, and Unix milliseconds for Cardano. It shows the last reported chain tip and reports an unavailable node or mismatched genesis. It does not detect every spend, run while the page is closed, send notifications, or claim/refund funds. A stalled or dishonest node may report stale state. Do not put secrets in a watch label.

The desktop wallet's **Swaps** page opens the separately started local board in an isolated Electron window with no access to the desktop wallet API and network access restricted to the loopback board and companion. Standard browser wallet extensions are not installed in that window; use a regular browser for those extensions. The board offers manual local actions but does not coordinate a complete transaction flow. The desktop bundle can be checked with `npm run typecheck --prefix hegemon-app` and `npm run build --prefix hegemon-app`; `node --test swap-service/desktop.test.mjs` runs the sandbox-window test when Electron and a local display (or virtual X display) are available. That test substitutes a dummy node executable so it does not start a real Hegemon node.

The development desktop app can also add a separate v0.11 pre-mainnet relay profile from **Node → Configuration → Add v0.11 testnet node**. Start it explicitly with **Start node**; stop a previously managed node first. It defaults to `~/.hegemon-node-v0.11`, checks the packaged release manifest and keeps RPC on loopback with mining disabled. Preserve any old node data and wallet files; do not select a legacy data directory for this profile. The network-identity indicator checks genesis, chain ID and manifest digest, but does not establish that the node is synced or on the canonical tip. Funded v0.11 GUI wallet and swap actions remain unimplemented; use the release's `private-spend` CLI for qualified wallet operations. `node --test swap-service/desktop-node-profile.test.mjs` exercises the profile through a fake executable and does not join the public network.

The experimental secret-backup panel generates a 32-byte preimage locally, displays only its SHA-256 hashlock, and encrypts the preimage with a separate user passphrase using PBKDF2-SHA-256 (600,000 iterations) and AES-256-GCM. The encrypted envelope stays in browser storage and can be copied out and imported in another browser. It stores the preimage only, not wallet keys, refund handoffs or complete swap terms. Export and test a backup before relying on it, and protect the passphrase separately. The panel requires the browser Web Locks API to prevent concurrent tabs from overwriting each other's local records; malformed local storage is not silently overwritten. The local server supplies the JavaScript, so a compromised server could serve code that steals the passphrase or preimage. This feature has not been independently audited and does not yet execute claims.

Encrypted backups use transactional IndexedDB records. Earlier version-1 local-storage backups are migrated under the cross-tab lock; the old copy is removed only after the new transaction commits. Malformed or conflicting old records stop the migration without overwriting either copy. Close older versions of the board before relying on a migration, and keep an independently tested export. The migration and browser storage are not substitutes for a durable backup.

The local action journal saves the public terms of each requested wallet action in transactional IndexedDB before the request is sent, then records the returned transaction or preparation identifier. A pending or uncertain entry may have been submitted: check the wallet or chain before retrying. The journal accepts no password, signing key, preimage or signed transaction, but addresses, amounts and activity can still be sensitive. Export its JSON and protect it separately; clearing browser data removes its local copy. Imports reject malformed, secret-bearing or conflicting records without overwriting existing entries. Up to 200 records are retained, and a damaged or full journal blocks new actions until it is addressed. This journal is not a wallet backup, a refund handoff, a confirmation monitor or complete swap recovery.

The selected offer's paired-leg check captures public terms from the local verification forms and rechecks both escrows against the offer's asset identifiers, quantities and common hashlock. The terms are in the offer owner's give/receive order. For a Cardano native-asset offer the UTxO must contain that single native asset, plus the separately specified ADA deposit. The check displays separate snapshots and remaining time in each chain's native units; it does not authenticate either participant or their addresses, prove that both outputs remain unspent after the snapshots, calculate safe cross-chain timeout margins, or establish finality. The Cardano UTxO query does not establish confirmation depth. These checks do not authorize a claim or coordinate a swap.

## Observing local claim preimages

These tools read confirmed local-chain data and write a new encrypted backup compatible with the board; they do not verify the other leg or execute a swap. The backup directory must be user-owned mode 0700. The passphrase is entered twice in the local terminal. The node and observation service must be trusted, and confirmation depth is not finality: a preimage seen in a transaction may remain public even if that transaction is later reorganized away. A disconnected observer must be restarted from an independently checked checkpoint.

For Bitcoin, run `python3 scripts/watch_bitcoin_preimage.py --bitcoin-rpc http://127.0.0.1:18443 --bitcoin-cookie /private/bitcoin/regtest/.cookie --bitcoin-genesis HEX --txid FUNDING_TXID --vout INDEX --hashlock HEX --start-height HEIGHT --output-dir /private/backups`. It scans the exact funding outpoint's confirmed witnesses on a peerless regtest node. For Hegemon, run `python3 scripts/watch_hegemon_preimage.py --hegemon-rpc http://127.0.0.1:9944 --hegemon-manifest /private/manifest.json --hegemon-genesis HEX --hashlock HEX --start-height HEIGHT --output-dir /private/backups`. It checks released preimages in canonical Development private-spend action bytes; node proof acceptance is trusted. Both default to two confirmations and stop if the observed chain changes. Bitcoin scans at most 10,000 blocks, Hegemon at most 512. These limits and thresholds are local-test choices.

For Cardano, start Ogmios against the already running, isolated node with `ogmios --node-socket /private/cardano/node.socket --node-config /private/cardano/configuration.yaml --host 127.0.0.1 --port 1337 --include-transaction-cbor`. It does not start a Cardano node or connect it to a public network. Record a trusted checkpoint slot and block hash from before the claim. Then run `python3 scripts/watch_cardano_preimage.py --ogmios-url ws://127.0.0.1:1337 --ogmios-pid PID --cardano-node-pid PID --cardano-socket /private/cardano/node.socket --cardano-network-dir /private/cardano --cardano-genesis SHELLEY_GENESIS_SHA256 --checkpoint-slot SLOT --checkpoint-hash HASH --outref FUNDING_TXID#INDEX --hashlock HEX --output-dir /private/backups`. The observer binds Ogmios to the configured local node, checks the transaction body hash, identifies the redeemer for the exact spent input and waits for two local blocks by default. It stops on a rollback or ancestry change. Install the Python dependencies from `scripts/requirements-htlc-local.txt` and `cryptography`; `scripts/check_cardano_preimage_observer.py` exercises the reader against a disposable local node. The tested Ogmios binary was v7.0.0 on x86-64 Linux, SHA-256 `73881dc5f9a6ad2831381c449c87b8620fb39f81f4c085e3a32965b925d9af57`; it is a separate optional dependency and is not bundled with the relay.

For local Ethereum, enter the original escrow terms in the action form, specify a block at or before the claim, and use **Observe confirmed Ethereum claim**. It checks the source-pinned runtime, claim event, receipt and local chain anchor before encrypting the recovered preimage in the browser. The browser and its provider must be trusted. Export and protect the encrypted backup, then import it in the other participant's local board or configure the appropriate companion to unlock it. These are manual recovery steps, not a continuously running watcher or automatic cross-chain claim.
