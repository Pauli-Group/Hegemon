# Local offer relay prototype

This is a local, noncustodial offer directory and opaque message relay. It has no wallet, keys, on-chain validation, matching engine, or swap execution. Offers and reservation credentials do not authorize any transaction. Clients must verify all chain data, maintain their own recovery records, and never send private keys or hashlock preimages to this service.

Run with Node.js 24 or later from the repository root:

    SWAP_DB=/private/path/offers.sqlite SWAP_PORT=8787 node swap-service/server.ts

The default listener is `127.0.0.1:8787`. Keep the SQLite file private. Use `node --test swap-service/server.test.mjs` for the local HTTP and restart tests. The relay is a prototype without public-deployment hardening, authentication of wallet identities, transport security, spam controls or production operational procedures.

## HTTP API

All endpoints return JSON and refuse request bodies over 16 KiB. Times are Unix seconds. `POST /offers` takes exactly `visibility` (`public` or `private`), `expires`, `give`, and `receive`. Each asset object has exactly `chain`, `kind`, `id`, and decimal integer string `amount`. Supported chain/kind pairs are `ethereum` with `eth`, `erc20`, `erc721` or `erc1155`; `cardano` with `ada` or `native`; `bitcoin` with `btc`; and `hegemon` with `hgn`. For ERC-20, the ID is its 0x-prefixed 20-byte address; for ERC-721 and ERC-1155 it is `address:decimal-token-id`; for Cardano native tokens it is `policy-id.asset-name`, both hexadecimal, with a 28-byte policy ID and zero to 32 asset-name bytes. Native coins use an empty ID. ERC-721 quantity is one. The relay checks syntax only; clients must authenticate asset identities and rules on chain. Offers expire between one minute and seven days after creation. The response contains an unpredictable `id` and `ownerToken`; store the owner token privately.

`GET /offers` lists at most 100 live public offers. `GET /offers/{id}` retrieves an offer when its random ID is known; possession of that ID is the private offer link capability, not authentication of a counterparty. `POST /offers/{id}/reserve` acquires one exclusive reservation until the earlier of 24 hours and offer expiry. It returns a confidential `reservationToken`; repeated reservations conflict until the existing reservation expires. An expired reservation's messages are discarded before a new participant joins.

Both owner and current reserver may use `Authorization: Bearer <token>` with `POST /offers/{id}/messages` and body `{"ciphertext":"<base64>"}`, or `GET /offers/{id}/messages?after=<id>`. The relay cannot verify whether payloads are actually encrypted. The local browser board uses AES-256-GCM with a random key in the shared link fragment and binds ciphertext to the offer ID. Anyone with that link can impersonate a participant; verify identities separately. A malicious server that serves modified client code can steal the key, so this prototype does not protect against a hostile service operator. Never transmit wallet keys or hashlock preimages. Clients must persist messages they need for recovery. The relay stores at most 100 messages per reservation. `POST /offers/{id}/close` requires the owner token and prevents new reservations; it does not affect on-chain escrows. Message posting requires an unexpired offer, and the reserver can read messages until its reservation expires. The owner can still read retained messages after offer expiry. A reservation or server availability is never proof of funding or of exclusive ownership of an asset.

The relay also serves the local offer board at `http://127.0.0.1:8787/`. The board can request read-only Ethereum and Cardano browser-wallet connections; it does not sign transactions or execute swaps. Wallet support varies by extension and network. Owner and reservation credentials are stored in browser local storage; clearing it loses access to those relay controls. These credentials are not wallet keys. Private offer links contain the unguessable offer ID and message key and must be shared only with the intended counterparty. A public-board viewer needs the owner to share that full link before encrypted conversation is possible. Localhost links work only on the same machine.

Run `node --test swap-ui/crypto.test.mjs swap-service/server.test.mjs` to check ciphertext authentication and the relay API. To run the two-session browser test from the repository root, install its development-only dependency with `npm ci --prefix swap-service`, install Chromium, and run `node --test swap-service/browser.test.mjs`. Set `CHROMIUM_PATH` if Chromium is not at `/usr/bin/chromium`.

The board also contains a read-only local Ethereum escrow verification form. It checks the exact pinned contract runtime and agreed fields, unspent state and holdings at both a two-confirmation snapshot and the current head through the connected browser provider. It accepts local chain ID 31337 only. The provider can lie or the chain can reorganize; a successful check also cannot prevent token issuer restrictions. It does not create, sign, or submit an escrow. Verify the reference terms independently.

Rebuild both Ethereum contracts using the pinned Foundry/solc versions before testing. From the repository root run `python3 scripts/export_token_escrow_template.py --check` and the same command with `--native --check` to confirm the bundled runtime templates match the compiled source. `python3 scripts/check_ethereum_escrow_verifier.py --output /workspace/new-verifier-run` tests native ETH and each token kind against fresh local contracts. `node --test swap-service/browser.test.mjs` also exercises the form against a real local Anvil node; it requires the Anvil executable and the development-only Chromium dependency described above.
