# Local offer relay prototype

This is a local, noncustodial offer directory and opaque message relay. It has no wallet, keys, on-chain validation, matching engine, or swap execution. Offers and reservation credentials do not authorize any transaction. Clients must verify all chain data, maintain their own recovery records, and never send private keys or hashlock preimages to this service.

Run with Node.js 24 or later from the repository root:

    SWAP_DB=/private/path/offers.sqlite SWAP_PORT=8787 node swap-service/server.ts

The default listener is `127.0.0.1:8787`. Keep the SQLite file private. Use `node --test swap-service/server.test.mjs` for the local HTTP and restart tests. The relay is a prototype without public-deployment hardening, authentication of wallet identities, transport security, spam controls or production operational procedures.

## HTTP API

All endpoints return JSON and refuse request bodies over 16 KiB. Times are Unix seconds. `POST /offers` takes exactly `visibility` (`public` or `private`), `expires`, `give`, and `receive`. Each asset object has exactly `chain`, `kind`, `id`, and decimal integer string `amount`. Supported chain/kind pairs are `ethereum` with `eth`, `erc20`, `erc721` or `erc1155`; `cardano` with `ada` or `native`; `bitcoin` with `btc`; and `hegemon` with `hgn`. For ERC-20, the ID is its 0x-prefixed 20-byte address; for ERC-721 and ERC-1155 it is `address:decimal-token-id`; for Cardano native tokens it is `policy-id.asset-name`, both hexadecimal, with a 28-byte policy ID and zero to 32 asset-name bytes. Native coins use an empty ID. ERC-721 quantity is one. The relay checks syntax only; clients must authenticate asset identities and rules on chain. Offers expire between one minute and seven days after creation. The response contains an unpredictable `id` and `ownerToken`; store the owner token privately.

`GET /offers` lists at most 100 live public offers. `GET /offers/{id}` retrieves an offer when its random ID is known; possession of that ID is the private offer link capability, not authentication of a counterparty. `POST /offers/{id}/reserve` acquires one exclusive reservation until the earlier of 24 hours and offer expiry. It returns a confidential `reservationToken`; repeated reservations conflict until the existing reservation expires. An expired reservation's messages are discarded before a new participant joins.

Both owner and current reserver may use `Authorization: Bearer <token>` with `POST /offers/{id}/messages` and body `{"ciphertext":"<base64>"}`, or `GET /offers/{id}/messages?after=<id>`. The relay cannot verify whether payloads are actually encrypted. The local browser board uses AES-256-GCM with a random key in the shared link fragment and binds ciphertext to the offer ID. Anyone with that link can impersonate a participant; verify identities separately. A malicious server that serves modified client code can steal the key, so this prototype does not protect against a hostile service operator. Never transmit wallet keys or hashlock preimages. Clients must persist messages they need for recovery. The relay stores at most 100 messages per reservation. `POST /offers/{id}/close` requires the owner token and prevents new reservations; it does not affect on-chain escrows. Message posting requires an unexpired offer, and the reserver can read messages until its reservation expires. The owner can still read retained messages after offer expiry. A reservation or server availability is never proof of funding or of exclusive ownership of an asset.

The relay also serves the local offer board at `http://127.0.0.1:8787/`. Wallet connections are read-only until a user explicitly requests an experimental local action described below. The board does not coordinate or execute complete swaps. Wallet support varies by extension and network. Owner and reservation credentials are stored in browser local storage; clearing it loses access to those relay controls. These credentials are not wallet keys. Private offer links contain the unguessable offer ID and message key and must be shared only with the intended counterparty. A public-board viewer needs the owner to share that full link before encrypted conversation is possible. Localhost links work only on the same machine.

Run `node --test swap-ui/crypto.test.mjs swap-service/server.test.mjs` to check ciphertext authentication and the relay API. To run the two-session browser test from the repository root, install its development-only dependency with `npm ci --prefix swap-service`, install Chromium, and run `node --test swap-service/browser.test.mjs`. Set `CHROMIUM_PATH` if Chromium is not at `/usr/bin/chromium`.

The board also contains a read-only local Ethereum escrow verification form. It checks the exact pinned contract runtime and agreed fields, unspent state and holdings at both a two-confirmation snapshot and the current head through the connected browser provider. It accepts local chain ID 31337 only. The provider can lie or the chain can reorganize; a successful check also cannot prevent token issuer restrictions. It does not create, sign, or submit an escrow. Verify the reference terms independently.

Rebuild both Ethereum contracts using the pinned Foundry/solc versions before testing. From the repository root run `python3 scripts/export_token_escrow_template.py --check` and the same command with `--native --check` to confirm the bundled runtime templates match the compiled source. `python3 scripts/check_ethereum_escrow_verifier.py --output /workspace/new-verifier-run` tests native ETH and each token kind against fresh local contracts. `node --test swap-service/browser.test.mjs` also exercises the form against a real local Anvil node; it requires the Anvil executable and the development-only Chromium dependency described above.

## Local companion

`scripts/local_swap_companion.py` is a separate process that binds only `127.0.0.1:8788`; it is read-only unless Hegemon actions are explicitly enabled. It can check configured Bitcoin regtest and isolated Cardano nodes, and it can ask the local `private-spend` wallet to verify Hegemon terms. It accepts requests only from the configured local web origin with a random pairing token, and supports no arbitrary commands or client-selected paths. The UI sends the token directly to the companion and holds it only in page memory; it does not send it to the offer relay. A malicious local service that serves altered UI code could still steal the pairing token, and same-user processes are not isolated from each other.

Create a new private directory and start the companion from a local terminal, substituting the paths and ports of the already running isolated test nodes:

    mkdir -m 700 /private/new-companion-dir
    python3 scripts/local_swap_companion.py --token-file /private/new-companion-dir/token \
      --bitcoin-rpc http://127.0.0.1:18443 --bitcoin-cookie /private/bitcoin/regtest/.cookie \
      --cardano-socket /private/cardano/node.socket --cardano-network-dir /private/cardano

Either chain's pair of options can be omitted. For a Hegemon wallet, add `--hegemon-wallet /private/wallet.store --hegemon-manifest /private/manifest.json --hegemon-genesis HEX --hegemon-rpc http://127.0.0.1:9944`. All four Hegemon options are required together. Hegemon verification is available only from an interactive local terminal, on a peerless Development node with the configured genesis. The companion displays the request for local approval and asks for the wallet passphrase in that terminal for each verification. It briefly holds the passphrase in process memory and passes it to `private-spend` over a pseudo-terminal; the browser and offer relay do not receive it. The wallet command reveals only a verification result, position and heights, not the decrypted note opening.

Open the board at `http://127.0.0.1:8787/`, read the pairing token from the mode-0600 token file locally, and enter it into the board's companion field. The token is a local capability, not a wallet password; do not share it. The default allowed origin is exactly `http://127.0.0.1:8787`. The UI currently expects the companion on port 8788. Cardano verification checks the validator, datum and exact asset value at a node tip; its confirmation depth remains unknown. Bitcoin requires two regtest confirmations. Hegemon defaults to two confirmations and two remaining blocks. These short local thresholds are not public-chain safety margins. Each verifier trusts its local node and requires independently authenticated expected terms.

`PYTHONPATH=scripts python3 -m unittest scripts/test_local_swap_companion.py` checks private pairing-token file handling and exact Cardano decimal conversion. The local pairing scripts exercise the Bitcoin and Cardano companion endpoints against actual fresh nodes; their output directories contain disposable keys and pairing tokens and must remain private.

For experimental manual Hegemon actions, create a separate user-owned mode-0700 handoff directory and add `--enable-hegemon-actions --hegemon-handoff-dir /private/handoffs` to the Hegemon companion invocation. Every typed action is displayed for explicit approval in the companion terminal. Wallet and encrypted handoff passphrases, and claim preimages, are entered there and are not sent by the browser. Preparing an action and submitting it are separate requests. Lock preparation creates an encrypted refund handoff in the specified directory; back it up and protect its separate passphrase. If a response is lost, the wallet may still have submitted or reserved funds: check wallet status before retrying. Submission acknowledgements contain a 32-byte preparation attempt ID and a different 48-byte action ID, and do not establish confirmation. These local actions do not verify the other leg or enforce safe cross-chain deadlines. Preimages become public when a claim is submitted and can remain public even after a reorganization.

Alternatively, save a browser-exported encrypted preimage backup as a user-owned mode-0600 JSON file and start the action companion with `--hegemon-preimage-backup /private/backup.json`. A claim then asks for the backup passphrase in the local terminal and decrypts the saved preimage locally instead of asking the user to type it. The backup file is selected only at companion startup, never by a browser request. This optional path requires Python's `cryptography` package. It has an interoperability test against the actual browser export; it has not yet been exercised in a complete Hegemon claim. Python and its cryptography library may retain temporary secret copies in process memory. The backup stores only the preimage, not the wallet, handoff or complete swap record.

For experimental Ethereum transactions, start the companion with `--ethereum-rpc http://127.0.0.1:8545` pointed at an already running, non-forked Anvil node. After pairing, the board exposes a deployment form. It compares the connected wallet's chain ID, genesis and head to this trusted local node before requesting wallet approval. Native ETH is funded at deployment. A token escrow is initially unfunded: after the deployment receipt, enter its address with the same agreed terms, submit a separate token approval, confirm its receipt, then submit funding and verify the funded escrow. The form checks the source-pinned code, exact terms and local state before approval or funding, and simulates the requested call. ERC-1155's operator approval covers all IDs in that token contract, not just the offered ID; use the separate revoke button and check its receipt after funding. Record each transaction ID and check its receipt; a lost response is ambiguous and must not be retried without checking wallet history. This is limited to local Anvil and is not a complete swap. Token issuers and nonstandard token behavior can still prevent transfers.

After expiry, the same form can submit a refund from the original refund address. It checks the pinned code and agreed terms, funded/unspent state, chain identity and timestamp, then simulates the refund before requesting wallet approval. The user must still check the receipt and confirmations. A claim interface and cross-chain coordination are not yet implemented.

The local deadline watch saves a label, chain, genesis hash, deadline and warning threshold in browser storage, and polls the connected local provider while the page is open. Its values are block heights for Bitcoin and Hegemon, Unix seconds for Ethereum, and Unix milliseconds for Cardano. It shows the last reported chain tip and reports an unavailable node or mismatched genesis. It does not detect every spend, run while the page is closed, send notifications, or claim/refund funds. A stalled or dishonest node may report stale state. Do not put secrets in a watch label.

The desktop wallet's **Swaps** page opens the separately started local board in an isolated Electron window with no access to the desktop wallet API and network access restricted to the loopback board and companion. Standard browser wallet extensions are not installed in that window; use a regular browser for those extensions. This is an offer and verification prototype, not an integrated transaction flow. The desktop bundle can be checked with `npm run typecheck --prefix hegemon-app` and `npm run build --prefix hegemon-app`; `node --test swap-service/desktop.test.mjs` runs the sandbox-window test when Electron and a local display (or virtual X display) are available. That test substitutes a dummy node executable so it does not start a real Hegemon node.

The experimental secret-backup panel generates a 32-byte preimage locally, displays only its SHA-256 hashlock, and encrypts the preimage with a separate user passphrase using PBKDF2-SHA-256 (600,000 iterations) and AES-256-GCM. The encrypted envelope stays in browser storage and can be copied out and imported in another browser. It stores the preimage only, not wallet keys, refund handoffs or complete swap terms. Export and test a backup before relying on it, and protect the passphrase separately. The panel requires the browser Web Locks API to prevent concurrent tabs from overwriting each other's local records; malformed local storage is not silently overwritten. The local server supplies the JavaScript, so a compromised server could serve code that steals the passphrase or preimage. This feature has not been independently audited and does not yet execute claims.

Encrypted backups use transactional IndexedDB records. Earlier version-1 local-storage backups are migrated under the cross-tab lock; the old copy is removed only after the new transaction commits. Malformed or conflicting old records stop the migration without overwriting either copy. Close older versions of the board before relying on a migration, and keep an independently tested export. The migration and browser storage are not substitutes for a durable backup.
