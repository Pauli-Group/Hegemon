# Hegemon v0.11.3: public wallet submission and sync maintenance

v0.11.3 adds an explicitly selected `public-submit` RPC policy for
third-party wallets. It exposes the existing safe surface plus the existing
PrivateSpend `hegemon_submitAction` route, with bounded admission and separate
public verification capacity. Keys, note recovery and proving remain client-side.
See [wallet integration and operator instructions](../PUBLIC_SUBMIT_WALLET_INTEGRATION.md).

The product software release is `0.11.3`; the network release remains `v0.11`.
Internal Cargo package versions deliberately stay at `0.10.0` for `hegemon-node`,
`wallet` and `walletd`, and `0.1.0` for `protocol-versioning`. The exact bytes of
`Cargo.lock` are an input to `circuits/transaction/src/private_spend.rs`'s
`relation_digest`; bumping those package versions would change the lock and
therefore the proof identity. Preserve lock SHA-256
`1c243bf3858f4ee22fa4441c7a2ee6d49b16d264147b0f3a2de845e760821719`.
`protocol_versioning::RELEASE_VERSION` and candidate/packaging metadata carry the
new software label; internal package metadata is not the release label.
Consensus, genesis/network identity, chain data, circuit/crypto version numbers,
transaction/proof formats, cryptographic parameters and wallet encryption are
unchanged. Existing nodes do not require coordinated activation. The common
PrivateSpend proof hides its private witness branch; the RPC policy filters
explicit action families and does not claim ordinary-only hidden-branch filtering.

## Source composition and release identity

The source starts from v0.11.2 tag commit
`15c42e687b24d9cb35bb6dbde6061459d6f1242a`, including the sync, CPU readiness,
transport and known-loser admission maintenance fixes. It also integrates the
reviewed non-consensus change
`af9a05cac18b663832d6bbacce4b634c81937779`.

The public-submit implementation is composed with the newer deployed sync-import
maintenance source `1e56a5c8f97eb6f8abf3e79a728849272c42dd0d`. This retains
nonblocking sync-control admission, best-announcement preparation outside the
receive loop, early stored-block checks and their source/runner qualification
repairs. Runtime merge `d283a1da545864dafb20d798ec3a5fccfa1c08b5` records that
composition; it is not, by itself, final build or release acceptance. The combined
source requires its own qualification rather than inheriting a pass from either
predecessor.

The published v0.11.2 tag and artifacts remain historical. Its artifact profile
binds source `e2fcbe4df99025d3b955d5053ebc1f21436db6f2`; those binaries cannot be
relabeled as v0.11.3. `config/v0113-release-candidate.json` is a pending preparation
record, not an accepted release profile. Final source commit, build manifest and
artifact checksums must come from the actual completed candidate. Null fields
mean that evidence has not yet been recorded.

From the final candidate checkout, build the new artifacts with
`scripts/build_release_artifacts.sh`. This creates the normal source-bound
four-binary manifest. Then prepare a separate local inventory, for example:

```sh
python3 -B scripts/prepare_v0113_candidate.py \
  --manifest target/release/hegemon-release-artifacts.json \
  --expect hegemon-node:hegemon-node:target/release/hegemon-node \
  --expect wallet:wallet:target/release/wallet \
  --expect walletd:walletd:target/release/walletd \
  --expect wallet:private-spend:target/release/private-spend \
  --output target/release/v0.11.3-candidate.json
```

Use `.exe` paths on Windows and target-specific paths for cross-builds. The tool
verifies current source/index provenance, native binary bytes, the `0.11.3`
product label, preserved internal package versions and exact frozen lock hash; refuses v0.11.2 build provenance; and writes only a new
`candidate_unqualified` record. It does not attest compiler execution, rewrite
accepted proof authority, run the network, publish or deploy. Retain build logs,
toolchain identity and measured results alongside the manifest.

## Preparation status and authorized rollout

At source preparation on 2026-11-07, release publication and deployment to the
two reference seed nodes are authorized. Required artifact qualification and
acceptance gates are still pending; this authorization is not a claim that the
release has passed them, been published or been deployed. Final manifests,
checksums and release/deployment receipts record the completed outcomes.

The authorized rollout preserves existing operator RPC configuration and does
not enable a new public-submit endpoint on either reference node. Public-submit
remains a separate explicit opt-in. No mainnet launch authority or new
cryptographic production approval is granted by this maintenance release.

## Qualification and rollout checklist

1. Preserve every relation-digest input, including the exact Cargo.lock and
   internal package versions. Freeze the scoped candidate source and record its exact commit/tree, lockfile
   hash, compiler identity, build command and actual binary checksums. Preserve
   the original v0.11.2 artifact and authority records.
2. Complete pure policy, CLI/launcher, actual HTTP, CORS and resource tests. Record
   the public positive transfer's exact unchanged action/proof identity and its
   production source/state authorization. Include malformed/oversized/inactive/
   wrong-network/unsupported-family rejection, pre-parse HTTP and additional-batch
   charging, duplicate suppression, client exhaustion, forged headers, public
   saturation with local capacity, disconnect/failure/worker-completion and
   response-body ownership, and heavy safe reads. Compatibility stubs remain
   directly refusing while discovery omits them.
3. Regenerate Lean vectors and run them against production Rust helpers. Record
   theorem-to-production and call-order obligations. Run required formal-core,
   formal-crypto, parser, source-authorization, launcher, dependency and binary
   security gates. A baseline source-pin mismatch is a qualification issue;
   changing an accepted pin to obtain a passing result is not qualification.
4. Measure accepted and rejected proof work and memory on the intended service
   hardware. Record the load and concurrency conditions. Confirm the one-public-
   verifier/no-permit-wait-queue default and tune only with new measured evidence. Confirm
   actual source-authorized unchanged-proof lifecycle behavior, not only backend
   fixture verification or test-only authority.
5. Complete independent review and qualification for the exact candidate. Build
   and verify every supported release platform from the same source, prepare new
   platform manifests and joining archives with their own hashes, and check their
   new software identity against the unchanged network identity. Existing
   `package_v0112_release.py` remains exclusively for the old accepted artifacts.
6. Complete the required publication gates before using the authorization above
   to publish the v0.11.3 tag or assets. Retain the release evidence with the
   published checksums; do not substitute local checks for required release gates.
7. Use the authorized reference-node rollout above. Verify the approved network,
   genesis and seeds from the current release/operator source; check capacity and
   existing state/backup procedures; replace binaries through the normal operator
   process. Preserve the existing operator RPC settings; this rollout does not
   enable public-submit. New installations retain `safe` by default.
8. For an approved public endpoint, explicitly choose external binding, origin,
   limits and transport/proxy configuration. Verify `rpc_methods`, forbidden
   methods, browser access, valid inline submission and local capacity under
   controlled public load. A proxy shares its transport-IP bucket because all
   forwarded-address headers are ignored.
9. Monitor admission outcomes, verification latency and normal node progress.
   If rollback is required, disable public-submit or restore the retained approved
   v0.11.2 binary using the normal operator procedure. Do not delete node/wallet
   state or blindly retry uncertain spends. No migration or network activation
   is introduced by this policy.

Shared mining retains
`HEGEMON_SEEDS="hegemon.pauli.group:30333,devnet.hegemonprotocol.com:30333"`
unless a current approved rotation says otherwise. All miners on the same
network must use the verified list. Enable NTP/chrony: future-skewed timestamps
are rejected.

## Evidence boundary

The candidate record distinguishes local implementation, qualification,
release approval, publication and deployment. Formal admission properties do
not prove socket/proxy correctness, OS scheduling, absolute wall-clock or RSS
bounds, universal DoS resistance or network privacy. Admitted work can wait for
Tokio scheduling or locks; 16 KiB response frames and response-body reservations
do not bound socket counts, OS buffers or remote acknowledgement. The release must report
remaining failed, skipped or unexecuted gates explicitly. Backend-positive proof
fixtures alone do not establish a state-authorized public HTTP transfer.
