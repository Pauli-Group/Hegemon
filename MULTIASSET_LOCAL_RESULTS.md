# Local multi-asset HTLC results

These are Development and local-chain functional rehearsals, not production security qualification. All chains were fresh and isolated. The token implementations used are disposable test fixtures, not USDC, DJED, USDM or any other issued asset. The browser offer board and relay did not drive these tests; the scenarios use scripted wallet and node adapters. Test directories contain disposable private keys and must remain private.

Separately, ERC-20, ERC-721 and ERC-1155 fixtures each passed claim and refund on fresh local Ethereum chains (`/workspace/etok3/summary.json`). Cardano fixture tokens passed claim and refund on fresh local nodes (`/workspace/ctok2/summary.json`). Foundry reported 24 passing tests (9 native ETH and 15 token escrow), including tokens that debit the sender more than the escrow receives. Node.js tests covered the local offer relay, restart persistence, access checks and AES-GCM message authentication. A Chromium test created a private offer, exchanged encrypted messages between two separate browser contexts, and exercised read-only wallet connections using mocked browser providers. No real browser wallet was connected.

The first same-chain Cardano attempt (`/workspace/csswap1/summary.json`) failed because its expiry slots exceeded the fresh network's time horizon. The successful retry used a local epoch length of 5,000 slots so that both deadlines fell within the horizon; this is not a public-network timing policy. Hegemon proof processes in the two token scenarios took 90.781–199.178 seconds and peaked between 1,733,804 and 1,995,796 KiB in per-process samples while the two scenarios shared the machine. These are not controlled performance benchmarks.

No test establishes arbitrary-token compatibility, safe production timeout margins, reliable public-chain observation, reorganization handling, fee estimation, complete wallet integration, or independent security review. In particular, issuers can prevent transfers or change token behavior after escrow. The browser board has local verification and experimental manual actions but does not coordinate an on-chain swap. Receipts for the Hegemon-linked runs recorded the then-current commit but the harness was modified in the working tree; they are not source-bound release receipts.

A read-only Ethereum escrow verifier now reconstructs the expected runtime from the pinned compiler artifact and the agreed immutable terms, checks the code and asset holdings at a two-confirmation local snapshot, and rejects spent escrows. ETH, ERC-20, ERC-721 and ERC-1155 checks passed against actual local contracts (`/workspace/everify7/summary.json`), including mismatched terms, chain-change simulation, deadline limits, a real spend at the latest head and post-claim rejection. Chromium also verified actual local ETH and ERC-20 escrows through a test wallet provider and rejected a changed amount. A first browser fixture incorrectly supplied an extra constructor argument; the verifier rejected it, and the corrected test passed. The verification depends on an honest RPC provider and trusted local client code; it is not an audit, issuer guarantee, or public-chain finality policy.

The independent Bitcoin regtest output checker reconstructed the expected script and checked an unspent output with two confirmations in both BTC/ERC-20 and BTC/Cardano-token rehearsals (`/workspace/bveth2/summary.json` and `/workspace/bvada2/summary.json`). It rejected altered terms and spent outputs. Its first negative-key test used the same key in both script branches, which Bitcoin Core rejected at descriptor validation; the checker now rejects duplicate keys explicitly before invoking Core.

The Cardano checker compared a local UTxO with the pinned validator, the full inline datum and exact native-asset value (`/workspace/ecverify1/summary.json`); changed terms and a spent output were rejected. The CLI query supplies no independent inclusion history, so the result deliberately reports no confirmation depth. Both checks depend on an honest local node and independently authenticated expected terms.

The rebuilt Hegemon private-spend wallet was tested with a fresh local Hegemon/ERC-721 swap (`/workspace/hverify1/summary.json`). Its read-only check matched the private note against independently supplied amount, hash, addresses, deadline and secret-release setting; it rejected changed terms, insufficient confirmation and deadline margins, and the spent note. The local companion was then tested in a fresh Hegemon/ERC-20 swap (`/workspace/hcomp1/summary.json`): the test simulated terminal approval and passphrase entry, verified that the passphrase was not echoed, and rejected altered terms, bad pairing credentials and a different origin. A separate copied-chain test rejected a locally declined request without prompting for a passphrase (`/workspace/hdeny1/summary.json`). These checks rely on the trusted local node and wallet; the existing proof circuit was not modified.

A read-only loopback companion was also exercised against local Bitcoin and Cardano nodes (`/workspace/bcomp2/summary.json`, `/workspace/ccomp3/summary.json`). A local deadline watch stores only user-entered metadata in browser storage, binds each entry to the expected genesis, and reports chain-tip deadlines while the page is open. It does not detect all spends, notify while closed, submit claims, or establish public-network safety. The desktop bundle and isolation policy tests passed; an Electron window test opened the local board with a dummy node executable and verified it had no desktop wallet API. The board's wallet connections were exercised with mocked providers, not actual wallet extensions.

The local UI also generates and encrypts a 32-byte swap preimage in the browser, exports an encrypted backup, and can import and test-unlock that backup. Chromium exercised separate browser contexts, wrong passphrases, altered backups and corrupted storage. A subsequent concurrent-tab run exposed a missing backup in the original shared local-storage array, despite its cross-tab lock; the implementation was changed to transactional IndexedDB with fail-closed migration. Three repeated concurrent-tab runs and a later browser run passed; the browser test also covered idempotent migration and rejection of conflicting legacy backups. This stores only the preimage, not the rest of a swap or wallet recovery material. It has not been independently audited or connected to claim transactions. The local server supplying the JavaScript must be trusted.

The current token escrow additionally checks both the sender debit and the escrow credit during funding. New ERC-20 and ERC-1155 fixtures with extra sender debits were rejected; all six local token claim/refund cases and the pinned Ethereum verifier passed with the updated contract (`/workspace/etok4/summary.json`, `/workspace/everify8/summary.json`). A fresh Hegemon/token run passed with the updated contract (`/workspace/hcomp3/summary.json`).

The local deployment primitive was exercised against fresh non-forked Anvil chains for ETH, ERC-20, ERC-721 and ERC-1155 (`/workspace/edeploy2/summary.json`). It rejected incorrect and stale chain anchors without submitting. Separate approval and funding actions passed for the three token fixture kinds (`/workspace/efund4/summary.json`), rejecting changed terms and a second funding attempt; ERC-1155 operator revocation was checked against the fixture's operator map. The first funding rehearsal (`/workspace/efund1`) attempted verification before the funding transaction had two confirmations; the test was corrected to mine confirmations. An intermediate revocation test (`/workspace/efund3`) called a standard interface getter absent from the simplified fixture; the corrected test uses its actual getter. The browser form was exercised against local Anvil for ETH deployment and ERC-20 deployment, approval, funding and verification using a test wallet provider and a substituted companion HTTP transport. The relay and companion are not swap coordinators, and no real wallet extension was tested.

The first experimental Hegemon companion action rehearsal (`/workspace/hact1`) failed after a lock was submitted: the companion expected a 32-byte preparation ID where the wallet returns a distinct 48-byte action ID. The local submission may already have succeeded. The response parser now handles both IDs and has regression tests. Fresh Hegemon/ERC-20 claim and refund rehearsals passed through terminal-approved actions with canonical submission and zero-peer checks (`/workspace/hact2/summary.json`, `/workspace/hact3/summary.json`). No automatic retry is safe after an uncertain submission. Source files were edited while these long-running rehearsals were active, so they are not source-bound release receipts.

Experimental local Ethereum refunds passed for ETH and each fixture token kind after expiry (`/workspace/erefund1/summary.json`); early and repeated refunds were rejected without submission. These are isolated functional tests, not public-chain recovery qualification.

Manual local Ethereum claims passed for ETH and all three token fixture kinds (`/workspace/eclaim1/summary.json`). Each test first refunded, restored a local snapshot, rejected a wrong preimage without sending a transaction, and then claimed. Chromium generated an encrypted backup, rejected an incorrect passphrase, and claimed a separate local ETH escrow using a test provider. The claim form checks its own escrow but does not verify the other swap leg or establish safe cross-chain deadline margins.

On fresh peerless Bitcoin regtest, manual companion actions funded, claimed and refunded separate outputs (`/workspace/bact2/summary.json`). The test rejected a wallet with only the claim key when funding, an early refund, an altered amount, an already spent output, a bad pairing token, a client-supplied secret field and local denial. A repeat using encrypted wallets (`/workspace/bact3/summary.json`) exercised local passphrase entry and wallet relocking. Chromium exercised the Bitcoin form with a mocked companion. Before funding, a synthetic refund signature is created but not broadcast. These actions assume pre-imported private descriptors and use a fixed 500 satoshi local spend fee; they do not establish production safety.
