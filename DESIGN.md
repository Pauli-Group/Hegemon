## 0. Design goals (what we’re optimizing for)

The design goals are:

1. **One canonical privacy pool** (no fragmented upgrade pools).
2. **End-to-end PQ security**

   * No ECC, no pairings, no RSA anywhere.
   * Only:

     * Lattice-based KEM/signatures (NIST PQC: ML-KEM, ML-DSA, etc.), ([NIST][1])
     * Hash-based commitments, Merkle trees, PRFs,
     * Hash-based or STARK-style ZK.
3. **Transparent proving system**

   * No trusted setup.
   * SNARK/STARK based only on collision-resistant hashes (FRI-style IOPs etc.). ([C# Corner][2])
4. **Note-based mental model**: UTXO-ish “notes” with strong privacy, plus viewing keys.
5. **Upgradability**: built-in versioning and “escape hatches” for *future* PQ breaks.
6. **Secure, seamless, delighting UX**: wallet, release-coordination, and miner/operator touchpoints must keep the PQ stack invisible,
   provide ergonomic flows across devices, and surface positive confirmation cues so users feel safe and delighted without
   facing operational friction.

Everything else is negotiable.

### 0.2 Admin posture (production/testnet)

* **No sudo, validator session, or superuser module** in production/testnet genesis. The PoW chain runs without validator sessions.
* The live chain has no on-chain governance path. Protocol changes ship through socially adopted release lines and PoW uptake, not a built‑in superuser key.

The operator `hegemon-node` binary is native. It starts a fresh native chain, persists native block and shielded-state metadata in `sled`, mines PoW development blocks, syncs blocks and self-contained user pending actions over the Hegemon PQ service, and serves the current wallet/app/script JSON-RPC method names over HTTP. Peer action relay is deliberately limited to user-submitted actions that can pass the same durable mempool validation as local RPC submission. Local coinbase rewards remain miner-local block-template material; recursive candidate submissions are retired and are never selected for new blocks.

Native P2P uses authenticated TCP sessions plus bounded address coordination; configured seeds are bootstrap points, not permanent routing hubs. On connection, peers request and share capped dialable-address lists. A node bound to an unspecified interface may register `0.0.0.0:PORT` or `[::]:PORT` as a port hint: the receiver supplies only the transport-observed source IP and never reuses the inbound connection's ephemeral source port. Explicit self-registration addresses must use that same observed IP, preventing a peer from registering an unrelated third-party host. Learned endpoints pass admission before they are persisted or propagated: the learned pool retains at most 1,024 endpoints globally and four ports per IP. One-off dials rotate across that admitted pool with endpoint and shared-IP exponential retry backoff, one in-flight attempt per IP, bounded concurrency, and connect/handshake timeouts. A successful outbound admission clears stale retry history while the session is active; an inbound source port does not clear outbound retry state, and when a one-off session disconnects its endpoint and IP enter cooldown again so connect-then-close peers cannot rotate immediately through alternate ports. Startup applies learned admission in peer-store recency order, then reconnect selection admits at most one cached endpoint per IP and gives an approved seed precedence over stale cached ports on that IP; explicit imported peers and configured seed endpoints remain endpoint-addressed so legitimate same-host deployments continue to work. Long-lived nodes periodically query a rotating subset of their peers so nodes that joined later can enter the address cache. Automatic router port mapping is not enabled by the native launcher; accepting inbound peers still requires a public listener, firewall/NAT forwarding, or an explicitly configured caller of the network traversal API. Outbound-only nodes retain redundant routes through the approved seeds and learned public peers, but the current protocol is not a DHT and has no relay data plane.

Hegemon is still a pure PoW chain. ### 0.1 Explicit overheads relative to classical private-money stacks

Contributors routinely ask how these PQ and MASP design choices differ from classical ECC-based shielded pools. The high-level
costs are:

* **Cryptographic payload sizes** – ML-DSA/ML-KEM artifacts are orders of magnitude larger than the ECC keys, signatures, and
  ECIES-style ciphertexts used by classical private-money systems. Even though the spend circuit keeps the “prove key knowledge inside the ZK proof”
  model (so there are no per-input signatures), block headers, miner identities, and the note encryption layer all absorb PQ
  size bloat: ML-DSA-65 pk = 1,952 B vs ~32 B Ed25519, signatures = 3,309 B vs ~64 B, ML-KEM ciphertexts (note encryption)
  = 1,568 B vs ~80–100 B for Jubjub-based ECIES. Runtime AccountIds hash PQ public keys with BLAKE2 into SS58-compatible 32-byte
  identifiers so extrinsic signing and PoW seal verification share the same PQ scheme without changing address encoding.
  Network/consensus plumbing must therefore expect materially larger payloads.
* **Proof sizes and verification latency** – Trading Groth16/Halo2 for a transparent STARK stack removes the trusted setup but
  makes proofs much chunkier: tens of kilobytes with verifier runtimes in the tens of milliseconds, versus sub-kilobyte Groth16
  proofs with millisecond verification. The spend circuit, memo ciphertexts, and block propagation logic all need to budget for
  that bandwidth/latency overhead.
* **Circuit-level MASP costs** – Supporting multi-asset notes requires in-circuit sorting/aggregation of `(asset_id, delta)`
  tuples, introducing an \(O((M+N) \log (M+N))\) constraint factor that single-asset equations avoid. We explicitly accept
  this blow-up because it stays manageable at the target `M, N` and keeps the user model aligned with MASP-style semantics.

These considerations don’t change the core protocol, but they should show up in performance estimations, benchmarking, and any
communication that compares this system to the status quo.

## 1. Cryptographic stack (primitives only)

### 1.1 Signatures

Use *only* NIST PQC signatures:

* Primary: **ML-DSA** (Dilithium, FIPS 204) for “everyday” signatures. ([NIST][1])
* Backup: **SLH-DSA** (SPHINCS+, FIPS 205) for long-lived roots of trust (genesis multisig, release-signing keys, etc.). ([Cloud Security Alliance][3])

Where they're used:

* **Consensus / networking**:

  * Identity-bearing consensus profiles and authenticated network envelopes use ML-DSA where their explicit protocol rules require signatures.
  * Active native V2 block metadata is identity-free: miners do not attach a public key, identity commitment, or signature, and shielded coinbase actions express reward ownership.
  * PQ network identity seeds are generated from OS entropy, persisted under the node base path (for example `pq-identity.seed`) or provided via environment override, and never derived from public peer IDs.
  * PQ session establishment uses fresh OS-random KEM encapsulation seeds and transcript nonces for every handshake so reconnects between the same long-term identities cannot reuse AEAD key/nonce pairs. PQ Noise session HKDF labels/input ordering, role-to-key mapping, 96-bit nonce layout, counter overflow behavior, InitHello/RespHello/Finish signing preimage grammar, PQ-native handshake-to-channel composition, transport-completion facts, wrapper-completion facts, KEM OS-RNG seed-source facts, first and arbitrary bounded peer-frame slot/nonce admission, failed duplicate/future open preservation, same-role role-misbind rejection, and legacy secure-channel comparison are checked against executable Lean models. The production channel-safety certificate now explicitly proves OS-RNG ML-KEM seeds are not public-transcript-derived, fixed deterministic, or caller-provided test seeds before composing transcript-KDF and directional frame facts. The v8 wire/parser replay certificate additionally composes that channel proof with exact PQ handshake/session parser admission, no-trailing-byte facts, wrapper completion, duplicate/future/stale replay fail-closed facts, same-role misbind rejection, and the transcript-as-HKDF-salt boundary. Lean-generated vectors now also exercise KEM RNG-source cases, duplicate/future replay-admission cases, same-role role-misbind cases, bounded initiator/responder `SecureSession` frame sequences through production send/receive, raw ciphertext emission, raw open/decrypt paths, real `PqTransport::upgrade_outbound` / `upgrade_inbound` completion outputs, the shipped `network::pq_transport` plus `NativePqTransport` wrapper completion outputs, and schema-v8 production channel-certificate rows checked against pq-noise/network/native Rust constants. Formal-core also binds both pq-noise and legacy network ML-KEM encapsulation sites so `random_encapsulation_seed` must precede the supplied-seed encapsulation helper. The legacy secure channel derives separate initiator-to-responder and responder-to-initiator AEAD keys, and its KDF preimage labels, role-to-key mapping, nonce layout, counter overflow behavior, and failed-open receive-counter preservation are checked against an executable Lean model and focused production regressions. Network/PQ Noise trust-boundary frames use bounded postcard codecs (`HNW1`, `PNH1`, `PNS1`) rather than `bincode`.
  * Native discovery uses bounded `GetAddr`, `Addr`, and `RelayRegistration` coordination messages inside authenticated `HNW1` sessions. Address refresh rotates across connected peers; learned-address admission caps the pool globally and per IP, and only admitted endpoints are persisted or propagated. Learned one-off dials rotate across candidates, deduplicate active attempts per endpoint and IP, share retry backoff across ports on one IP, restore cooldown when a one-off session disconnects, and enforce connection timeouts. Cached startup reconnect targets are also deduplicated by IP, with configured seeds preferred over cached ports; explicit operator endpoints remain endpoint-addressed. Only the transport-observed IP plus a claimed listening port may define a self-registered public endpoint. The unsafe local topology RPC reports direct sessions; it does not imply DHT-wide graph knowledge.
  * Node identity records store optional PQ session keys as protocol metadata; registrations provide PQ bundles through native governance/release tooling when that surface is reintroduced.
* **User layer**:

  * Surprisingly little: within the shielded protocol, we can get rid of *per-input signatures* entirely and instead authorize spends by proving knowledge of a secret key in ZK; here we do it with hash/lattice PRFs rather than ECC.

So: signatures are *mostly* a consensus/network thing, not something you see for each coin input.

### 1.2 Key exchange / encryption

For note encryption and any “view key” derivation:

* Use **ML-KEM-1024 (Kyber, FIPS 203)** as the KEM to establish shared secrets. ([NIST][1])
* Use a standard AEAD like **AES-256-GCM** or **ChaCha20-Poly1305**:

  * Symmetric is already “quantum-ok” modulo Grover; 256-bit keys give you ~128-bit quantum security.

Design pattern:

* Each address has a long-term **KEM public key** `pk_enc` and an explicit `crypto_suite` identifier.
* For each note, sender:

  * encapsulates to `pk_enc`,
  * runs a KDF on the shared secret plus `crypto_suite` to get the AEAD key and nonce,
  * authenticates `(address_version, crypto_suite, diversifier_index)` as AEAD AAD.

This is a direct note-encryption analogue built on ML-KEM instead of ECC.

### 1.3 Hashes, commitments, PRFs

To avoid any discrete-log assumptions:

* **Conventional, typed hashes**:

  * Non-transaction consensus identities retain their version-owned conventional-hash types; a digest from one domain or width is never interchangeable with another.
  * Rejected V6/Epsilon descriptors used exact domain-framed SHAKE256-448 outputs for commitments, nullifiers, Merkle nodes and roots, ciphertext hashes, intent, balance, and transaction identities. Those domains are historical fixtures, not successor authority. Fresh test-only `HX448C02` compares two conventional 448-bit semantic registries while preserving policy, oracle, and attestation as direct live-compatible 384-bit fields; neither diagnostic profile is selected. Proof commitments and Fiat--Shamir for any successor must use conventional SHA-512/SHAKE at profile-fixed widths.
* **No field-friendly hash authority**:

  * Poseidon/Rescue-style relations remain useful historical experiments, but no Poseidon digest can authorize successor semantics, statement binding, consensus identity, or a proof transcript.
  * Every selected conventional-hash message bit and output bit must be constrained inside the proof and linked to its typed source or fixed frame constant. Host-side recomputation alone is not a relation.

Commitments:

* **Hash-based commitments** everywhere with versioned, typed conventional digests. Rejected V6 registered SHAKE256-448 frames and older BLAKE3/BLAKE2b/Poseidon constructions remain version-specific historical surfaces; the final registry is allocated only after compiled profile selection.
* **Note commitment tree**:

  * Same conceptual note-commitment tree throughout the stack, but using the global hash or the STARK hash consistently; no Pedersen, no Sinsemilla, no EC cofactor dance.

PRFs:

* All note identifiers and nullifiers are derived with explicitly framed keyed hashes. The following untyped notation is conceptual, not a successor byte grammar:

  * `sk_nf = H("view_nf" || sk_view)`
  * `nk = H("nk" || sk_nf)`
  * `nullifier = H("nf" || nk || note_position || rho)`

No group operations anywhere in user-visible cryptography.

STARK verifier parameters (hash function choice, query counts, blowup factors, field extension) are protocol-release parameters, not live runtime knobs. The transaction-proof family is also version-owned: `protocol/versioning` and `protocol/kernel/src/manifest.rs` must commit the exact backend before it can carry authority. Production transaction-proof routing currently accepts no binding, so the accepted production frontier remains empty. The current fail-closed implementation candidate is HGV8RP03/SMZ9 with a 122,863-byte maximum proof projection; the capability registry still returns `None`. `HGF6ST01`, `HGF6ST02`, `HGF6HR02`, `HGR6RM02`, and `HGV6PB02` are rejected historical candidate identities and may never be reinterpreted. The direct SmallWood Boolean adapter is outside the smallest-proof lane after its source-static hash-only relation projected to at least 1,258,569 engine rows and about 75.6 MB under the widened wire formula. Historical `HX448C02` is an 869-byte scalar diagnostic with 125 seven-byte limbs and 109 M4 words. It compares mixed unkeyed BLAKE2b-448/SHAKE256-448 with split SHA3-512/SHAKE256-448 on the same intended semantics, preserves three live-compatible 48-byte stablecoin authorities without reinterpretation, and mirrors lifecycle admission relative to a caller-supplied whole manifest and height. Its same-source M4 graph now emits 20 local non-hash, seven transaction hash-link, and nine consensus-state constraint groups over 109 statement plus 50 state words, including expected/provided manifest-root and height equality and lifecycle/freshness/cap predicates. Whole-manifest recomputation, selected-entry membership, policy-identity recomputation, and consensus authentication of the expected root/height remain explicitly outside the graph; aggregate scalar-to-M4 execution is absent, its M4/DCE geometry is uncompiled, and it allocates no production identity. `HX448C01` is retired. ## 2. ZK proving system: single STARKish stack

Rather than BCTV14 → Groth16 → Halo2, we pick **one** family: hash-based IOP → STARK-style.

Properties:

* **Transparent**: no trusted setup (only hash assumptions). ([C# Corner][2])
* **Post-quantum**: soundness reduces to collision resistance of the hashes + random oracle, so Shor has nothing to grab; generic quantum search only affects the symmetric margin rather than creating a public-key collapse.
* **Self-contained**: every transaction carries its own proof; recursion, aggregation, receipts, sidecars, and caches may never become validity authority.

Concretely:

* Base field: a 64-bit-friendly prime like 2⁶⁴×k−1 suitable for FFTs and FRI.
* Prover:

  * CPU-friendly (no big-integer pairings).
  * Highly parallelizable (good for GPU/prover markets).
* Verifier:

  * Proof sizes remain larger than SNARKs. Historical V4/Gamma SmallWood runs measured roughly 87--118 KB depending on the pre-hardening relation and profile, but none implements a qualifying successor relation or complete zero knowledge. They are not production proof-size points. The rejected SWV6 parser has a 512 KiB safety ceiling; that ceiling is not a measured proof cap.

**Lesson from legacy pool migrations:** we do *not* change proving systems mid-flight if we can avoid it. We pick one transparent, STARK-ish scheme and stick with it, using recursion for evolution rather than entire new pools.

Implementation detail: the retained SmallWood V4 frontend materializes sparse linear constraints plus an explicit nonlinear expression/root program over Hegemon Goldilocks, but its Poseidon transition family is legacy and cannot authorize a successor. The direct conventional-hash SmallWood adapter is also disqualified by its source-linked Boolean row and wire geometry. A fresh frontend must compile the entire fixed 2-input/2-output, all-16-encoding, stablecoin, and all-authorization-mode relation together with every source-linked constraint for the selected conventional hash schedule into whichever Boolean-native engine wins the complete-ZK/PQ128 tournament. Host validation, a scalar oracle, and a list of named constraints are not substitutes for one executable aggregate relation and independently refined verifier.

#### 2.1 Algebraic embeddings that claw back overhead

The transparent stack above is heavier than Groth16/Halo2, but a few circuit-level embeddings keep it manageable:

* **Goldilocks-friendly encodings** - Express note and balance logic directly in the 64-bit base field while range-constraining all monetary values to 61 bits. This keeps arithmetic compact without allowing raw u64 values to alias after field reduction.
* **Permutation/Ishai–Kushilevitz style lookups** – MASP balance checks need large-domain comparisons (e.g., `asset_id` equality during the in-circuit sort). The retained relation demonstrates STARK-friendly permutation arguments, but V6 must re-establish the exact lookup and sorting constraints without borrowing Poseidon authority.
* **Batched range proofs via radix embeddings** – Instead of per-note binary range proofs, the retained transaction AIR decomposes bounded values into 21 shared radix-8 limbs (`3` bits each, boolean top limb) and reuses one limb region across note, fee, value-balance, and issuance rows. V6 must compile and refine the same intended monetary bounds before this becomes production evidence.
* **Folded multi-openings for recursion** – Recursively verifying child proofs requires many polynomial openings; batching them through a single FRI transcript with linear-combination challenges keeps the verifier time in the "tens of ms" bucket despite the larger STARK proofs.

None of these tricks negate the inherent bandwidth hit of transparent proofs, but they make the witness columns thinner and the constraint system shallower so that prover time and memory stay near the current baseline even with PQ primitives.

### 2.6 Independent transaction proof mode

The active product path is an ordered chain of independent native SmallWood transaction proofs. Every shielded transfer carries one canonical `tx_leaf` artifact. Block authors preflight those proofs and publish no `proven_batch`, `block_artifact`, receipt root, commitment proof, or recursive candidate. Import verifies each transaction proof, its parent-state anchor, the ordered DA projection, and the resulting state transition through `InlineRequired`. Historical `recursive_block_v1` and `recursive_block_v2` artifacts remain readable only for replaying blocks that already contain them; the native `receipt_root` object is decode-only.

* Block authors include only the ordered shielded transfer actions and the miner-local coinbase action. Candidate-artifact actions are retired from new block construction.
* A chain-level `ProofAvailabilityPolicy` still has the wire values `InlineRequired` and `SelfContained` for compatibility. New blocks use `InlineRequired`; `SelfContainedAggregation` is entered only when replaying a historical block that already carries one recursive artifact.
* The shipped unsigned transfer format remains native `tx_leaf`; there is no product fallback to legacy inline STARK transfer verification.
* Non-empty shielded blocks fail closed unless every ordered native `tx_leaf` verifies and binds to the canonical statement, parent state, DA projection, and resulting state transition. New blocks fail closed if `proven_batch` or `block_artifact` is present.
* Authoring directly preflights the ordered transaction proofs through the consensus verifier before constructing mining work. Proof verification runs from a canonical snapshot without holding the node state lock; the template is used only if the tip and selected action bytes still match after verification. It does not build or wait for an aggregate.
* Local RPC and network-originated shielded transfers both complete full native `tx_leaf` verification before sled or in-memory publication. Semantic-hash single-flight and a bounded negative cache suppress repeated immutable failures even when arrival timestamps change. Separate one-lane peer, local, and template limits share a three-lane verifier cap, so an untrusted peer cannot consume local or mining capacity. A batch failure isolates proofs in parallel, durably quarantines only deterministic failures, and retries valid siblings once; startup applies the same sanitizer to persisted rows. Candidate artifacts and externally submitted coinbases are rejected before mempool budgeting; coinbase actions are authored only by the mining path.
* Native sync, metadata, action-request projection, and action decoding are exact-admission gates: bounded sync messages reject legacy bincode and trailing bytes, SCALE and bincode helpers reject unconsumed bytes plus parser-accepted bytes that do not round-trip to the canonical encoding, native metadata load accepts only exact current identity-free `NativeBlockMeta`; retired identity-bearing V2, signed V1, and unsigned V1 encodings are identified and rejected, as are trailing or noncanonical encodings, `hegemon_submitAction` accepts only strict known JSON fields with empty wallet-compatible kernel-envelope fields, and block action payload counts must match the header before semantic validation. The Lean codec-admission package also proves the inverse non-malleability direction: accepted sync, exact-decode, current-only metadata, and block-action codec surfaces imply parser acceptance, full byte consumption, canonical exact re-encoding where applicable, current-format acceptance with legacy rejection, and action-count agreement. Non-empty unimplemented envelope fields such as object refs, authorization proofs/signatures, or aux data reject before `PendingAction` staging instead of being silently projected away. Action-request projection vectors now instantiate every supported submitAction route family before route-specific semantic validation: outbound bridge, inbound bridge, bridge verifier registration, inline transfer, sidecar transfer, sidecar transfer with empty staged proof bytes, candidate artifact, and coinbase. Candidate-artifact pending actions additionally require the live route payload bytes to exact-decode as `SubmitCandidateArtifactArgs` and match the duplicated `candidate_artifact`; malformed route bytes, artifact mismatch, and custom proof-kind routes are named Lean rejection surfaces with native regressions where production can instantiate the concrete enum. Coinbase pending actions now have raw `MintCoinbaseArgs` SCALE wire vectors checked through production exact decode. After exact decode, block actions must also satisfy embedded `tx_hash` recomputation and uniqueness before import or decode-only consumers observe them. Persisted pending-action reload is represented by a separate Lean-conformance-checked admission table: malformed sled keys, sled-key/embedded-`tx_hash` mismatch, recomputed `pending_action_hash` mismatch, and duplicate loaded hashes reject before locally reloaded actions can enter mining selection. These codec, action-request projection, action-hash, and pending-action reload boundaries are represented in Lean and checked against the production native helpers.
* The native block `action_root` transcript is Lean-conformance-checked before hashing: the root preimage is the fixed `hegemon-native-extrinsics-v1` domain, little-endian action count, and ordered 32-byte action hashes. BLAKE3 security/equivalence remains a separate assumption.

## 3. Ledger model: one PQ shielded pool, no transparent pool

### 3.1 Objects: notes and nullifiers

We keep the shielded-note mental model, but trimmed:

* A **note** is a record:

  * `value` (e.g. 64-bit or 128-bit integer)
  * `asset_id` (for a MASP-like multi-asset pool)
  * `pk_view` (recipient’s viewing key material, see below)
  * `rho` (per-note secret)
  * `r` (commitment randomness)
* The chain stores only:

  * a **commitment** `cm = Com(value, asset_id, pk_view, rho; r)` (48-byte, 6-limb encoding),
  * a Merkle tree of note commitments,
  * a **nullifier** `nf` when the note is spent (48-byte, 6-limb encoding).

The ZK proof shows:

* “I know some opening `(value, asset_id, pk_view, rho, r)` and nullifier secret `sk_nf` such that:

  * `cm` is in the tree,
  * `nf = PRF(sk_nf, rho, position, …)`,
  * total inputs = total outputs (value-conservation),
  * overflow conditions don’t happen.”

No ECDSA/EdDSA/RedDSA anywhere; the “authorization” is just knowledge of `sk_nf` inside the ZK proof.

Note: the switch to 6-limb 48-byte commitment/nullifier encodings is protocol-breaking. Any chain spec
that adopts this encoding requires a fresh genesis and wiping `node.db` plus wallet stores.

### 3.2 Transaction structure

A transaction includes:

* List of **input nullifiers** `nf_i`.
* List of **new note commitments** `cm_j`.
* Encrypted **note ciphertexts** for recipients (KEM+AEAD).
* One or more **STARK proofs** attesting the statements above.

Consensus checks:

* All `nf_i` are unique and not previously seen.
* STARK proofs verify.
* Block value balance is respected (including fees and issuance).

The PoW fork mirrors conventional PoW mechanics so operators can reason about liveness intuitively:

* Block headers expose an explicit `pow_bits` compact target, a 256-bit nonce, and a 128-bit `supply_digest`. Miners search over the nonce until the PoW work meets `target(pow_bits)`. A zero mantissa or compact encoding that decodes to target zero is invalid, and every PoW header must carry the seal
  (there is no “missing” difficulty case between retargets).
  Active fresh-chain native metadata carries no miner public key, signature, or commitment. Native block authority is proof of work
  plus the canonical block/action rules; reward ownership is expressed by the canonical shielded coinbase action. Removing the
  authority-free identity envelope saves its serialized bytes and an ML-DSA sign/verify per block while eliminating randomized-signature
  body malleability. Exact legacy unsigned/signed V1 and unreleased identity-bearing V2 metadata grammars are decoded only far enough
  to return an actionable fresh-genesis rejection and are never upgraded into active metadata. Generic consensus/P2P identities remain
  separate from this native active-V2 rule.
* Difficulty retargeting is deterministic: after the genesis-anchored launch window, every `RETARGET_WINDOW = 10` blocks the chain recomputes the target from the window's
  timestamps, clamping swings to ×¼…×4 and aiming for a `TARGET_BLOCK_INTERVAL = 60 s` (1 minute). The first boundary inherits the launch bits instead of treating the fixed genesis timestamp as a mined timing sample. Honest nodes reject any block whose
  `pow_bits` diverges from this schedule, which makes retarget spoofing impossible even across deep reorgs. Blocks between
  retarget boundaries MUST inherit the parent’s `pow_bits` verbatim and the retarget math uses the clamped timespan so outlier
  timestamps cannot skew difficulty even after a reorg. The retarget boundary schedule and compact re-encoding step are Lean-conformance-checked so retarget outputs cannot drift through skipped history, target truncation, or zero-target edge cases. The native verifier also requires the compact difficulty bits
  embedded in a PoW seal to equal the locally computed schedule exactly and checks work against that schedule target, not an attacker-supplied near match. The native node treats `NATIVE_DEV_POW_BITS` as the calibrated launch/genesis difficulty only: work templates, locally mined imports, announced blocks, replay, and sync validation compute the expected child bits from stored parent history before accepting or extending a chain.
* A PoW block may carry one shielded coinbase action, and if present it must be the final action; omitting it deliberately forfeits
  subsidy and fees. Multiple, first, or middle coinbases reject before proof/DA work. The coinbase spells out how many native units
  were minted and how many fees were aggregated. Consensus enforces
  `minted ≤ R(height)` where `R()` starts at the `TOKENOMICS_CALCULATION.md` initial subsidy and halves every 4-year epoch
  (`2_102_400` one-minute blocks; height 0 mints nothing).
  Shielded transfer `fee` values are interpreted as optional miner tips, so `fee = 0` remains valid and any provided tip is paid
  to the miner through the shielded coinbase note rather than a transparent balance credit. Nodes update the running
  `supply_digest = parent_digest + minted + fees − burns` inside a 128-bit little-endian counter that
  rejects underflows/overflows and compare it against the header before accepting the block. The Lean supply-chain invariant
  models those accepted header claims as an ordered replay, proves counterfeit claimed supply cannot validate against the executable
  deltas, and now connects accepted native transaction-chain deltas and canonical no-theft/public-field boundary facts to claimed-supply steps under an explicit fee/native-delta binding. It exports examples checked against the production PoW supply transition helper. Coinbase metadata that omits the
  balance tag or references an out-of-bounds transaction index fails validation.
* Ciphertext data availability is bound via `da_root` and deterministic parameters in the header. The block’s ciphertext blob is serialized in
  transaction order with length prefixes, erasure-coded with 1D Reed–Solomon (`p = ceil(k/2)` parity shards over `k` data shards),
  and Merkleized with BLAKE3 under `da-leaf`/`da-node` domain tags. Active V2 receives the full inline block body, derives the
  smallest canonical tier in `[1 KiB, 4 KiB, 16 KiB]`, recomputes the exact encoding/root, and rejects metadata or alternate-tier
  drift. `da_getChunk` is a bounded shard/opening service primitive; the shipped node does not yet schedule randomized sampling,
  so sampling-detection probabilities are conditional/future claims. The erasure code covers transfer ciphertext bytes only;
  transaction proof/action bytes are authenticated by the identity-free schema-3 chunked block-body locator and action root, not made reconstructable by
  this DA code. The unreleased identity-bearing schema 2 is rejected rather than upgraded. A known block receives no sync/fork-choice
  credit until its received locator exactly matches a freshly encoded stored canonical body in the bounded blocking import path;
  block-hash-keyed send-cache state is not trusted for that comparison. Range responses enter a metadata-only fair queue before
  sled loading: one outstanding request per peer, two active loaders globally, and a retained-plus-transient maximum-body reservation
  per loader bound decode/encoding memory while the async receive loop remains live. Sync scheduling and response bookkeeping read a
  compact `(height, block id)` tip snapshot rather than cloning the canonical action body; maximum-size blocks therefore do not turn a
  scalar Tokio-loop check into a 64 MiB copy. Sidecar transfer carriage remains decode-compatible research code but is inactive under V2’s inline-only policy.
* Timestamp guards match the implementation: the header time must exceed the median of the prior 11 blocks and be no more than
  90 seconds into the future relative to the local clock; nodes may re-evaluate future-dated candidates as time advances but
  still reject any header that remains beyond the skew bound or fails median-time-past.
* Block template helpers in `consensus/tests/common.rs` show how miners wire these fields together: compute the note/fee/nullifier
  commitments, attach the coinbase metadata, recompute `supply_digest`, and only then sign + grind the header.

No transparent outputs; everything is in this one PQ pool from day 1.

Native RPC endpoints expose that state machine so operators can monitor the same fields remotely. `/health`, `hegemon_consensusStatus`, and the compatibility `chain_*`/`system_*` methods report hash rate, mempool depth, stale share rate, best height, and compact difficulty values. Per `TOKENOMICS_CALCULATION.md`, the initial block reward is ~4.98 HEG (derived from the 60-second block time), and epochs last 4 years (~2.1M blocks). Blocks with an explicit shielded coinbase update the header’s `supply_digest`; empty/no-reward native blocks leave it unchanged. The quickstart playbook in [runbooks/miner_wallet_quickstart.md](runbooks/miner_wallet_quickstart.md) walks through querying those endpoints before wiring wallets to the node API. Proof verification is mandatory on production and development node imports; attempts to disable it are logged and ignored rather than changing block validity.

### 3.3 Shielded stablecoin issuance

Stablecoin issuance and burn are modeled as a non-native MASP asset that lives entirely inside the shielded pool. Instead of exposing a transparent mint, the transaction circuit allows a single asset id to carry a non-zero net delta, but only when the proof binds to a protocol policy hash plus the latest oracle and attestation commitments. The native policy identity is now the exact 61-byte SCALE tuple hashed by native-output-length RFC 7693 BLAKE2b-384 under the framed `hegemon.kernel.stablecoin-policy.v2` domain, yielding one 48-byte value. The balance kernel and production verifier reject native asset id, external padding sentinel, and the Goldilocks padding-field alias as stablecoin issuance assets before any mint exception is applied. Native admission consumes that exact policy hash and fail-closes enabled stablecoin payloads unless a plausible active manifest entry also satisfies lifecycle, freshness, dispute, issuance, and cap predicates. This hash migration is not successor-proof authority: the current kernel global root excludes stablecoin policies, the source manifest authorizes no live policy, and `HX448C02` accepts a caller-supplied manifest view without constraining equality to consensus state. A production state writer, authenticated manifest/root binding, oracle freshness source, fresh release identity, and refinement evidence remain required.

Issuance and burn therefore stay shielded: the proof shows `inputs - outputs = issuance_delta` for the stablecoin asset, and the runtime accepts the binding only through the unsigned proof-native lane. Wallet tooling assembles the binding from the active protocol state and submits it through the Hegemon shielded RPC, not through a signed account extrinsic. Normal stablecoin transfers do not require a binding, but they still ride the same MASP rules and never leave the privacy pool.

## 4. Addresses and keys (PQ shielded-address model)

We still want:

* **Spending keys**
* **Full viewing keys**
* **Incoming-only viewing keys**
* Public addresses derived from those.

### 4.1 Secret key hierarchy

```mermaid
flowchart TD
    ROOT[sk_root<br/>256-bit master secret]

    ROOT -->|HKDF "spend"| SK_SPEND[sk_spend]
    ROOT -->|HKDF "view"| SK_VIEW[sk_view]
    ROOT -->|HKDF "enc"| SK_ENC[sk_enc]
    ROOT -->|HKDF "derive"| SK_DERIVE[sk_derive]

    VK_NF -->|H "nk"| NK[nk - Nullifier key]

    subgraph Viewing Keys
        IVK[Incoming VK<br/>sk_view + sk_enc]
        FVK[Full VK<br/>IVK + vk_nf]
    end

    SK_VIEW --> IVK
    SK_ENC --> IVK
    SK_VIEW -->|H "view_nf"| VK_NF[vk_nf]
    VK_NF --> FVK

    SK_DERIVE --> ADDR[Diversified Addresses<br/>shca1...]
```

Let's define base secret material:

* `sk_root` – master secret for the wallet.
* Derive sub-keys via KDFs:

  * `sk_spend = H("spend" || sk_root)`
  * `sk_view = H("view" || sk_root)`
  * `sk_enc = H("enc" || sk_root)`

From this we derive:

* **Spending authorization material**:

  * `sk_spend` remains in the wallet for authorization/signing and is never embedded in viewing keys.
* **Nullifier key material**:

  * `nk = H_f("nk" || sk_spend)` is derived in-circuit from spend key material.
* **Viewing keys**:

  * `vk_full`: includes enough to derive incoming/outgoing note info plus a spend-derived nullifier PRF output for spentness tracking.
  * `vk_incoming`: only the KEM/AEAD decryption info and the ability to scan for your notes, not to reconstruct spends.

Everything is done via hash-based PRFs / KDFs; no ECC.

### 4.2 Address encoding

A **shielded address** contains:

* A version byte (for future evolution).
* A **crypto suite** identifier (the note-encryption parameter set).
* A **KEM public key** `pk_enc` (for ML-KEM).
* An **address-id / diversifier** derived from `sk_view` via PRF.

You can have multiple diversified addresses derived from the same underlying key material. Each address binds the crypto suite, ML-KEM public key, and recipient key derived from a diversifier index.

### 4.3 Wallet crate implementation

The repository now contains a `wallet` crate that wires these ideas into code:

* `wallet/src/keys.rs` defines `RootSecret`, `DerivedKeys`, and `AddressKeyMaterial`. A SHA-256-based counter expander (`wallet-hkdf`) produces `sk_spend`, `sk_view`, `sk_enc`, and `sk_derive`. The fresh-chain V3 profile derives the spend nullifier key, view nullifier key, and diversified recipient key through the centralized framed BLAKE2b-384 helper under three distinct registered domains, then explicitly takes 32 bytes for key material (a PQ128 preimage boundary, not a 384-bit collision-binding claim). Diversified addresses are computed deterministically from `(sk_view, sk_enc, sk_derive, index)`; the removed generic BLAKE3 helper is not a wallet or consensus API.
* `wallet/src/address.rs` encodes addresses as Bech32m (`shca1…`) strings that bundle the version, crypto suite, diversifier index, ML-KEM public key, `pk_recipient`, and spend-auth key `pk_auth`. Decoding performs the inverse mapping so senders can rebuild the ML-KEM key and note metadata.
* Private predicate threshold notes reuse the hidden `pk_auth` note slot as a policy commitment key derived from the private `policy_root`, threshold, and policy commitment randomness. The Rust note API exposes `PredicateThresholdPolicyOpening` and `PredicateThresholdSpendWitness` so witness-selected policy data must match the consumed note opening before authorization can continue. This is intentionally not an address or action-layer field: public signer sets, public m/n values, approval counts, approval nullifiers, and public authorization payloads remain out of the transaction surface. The future predicate satisfaction circuit or DSL must prove the threshold policy itself against this already-bound private opening.
* `wallet/src/multisig.rs` adds the wallet-side data model for stateful private accumulator multisig on the current proven SmallWood scope. Account creation stores the hidden threshold, hidden signer count, up to six hidden five-limb signer tags derived by the transaction circuit from each signer spend key, the `smallwood_policy_root_bytes(threshold, signer_count, padded_policy_signer_tags)` root, and policy commitment randomness inside the encrypted wallet; unsupported signer counts, zero thresholds, thresholds above signer count, duplicate tags, noncanonical tags, and active first-limb tag collisions fail closed. The circuit relation is fixed-size: active tags are sorted and padded to six private witness slots, and inactive slots are constrained to zero. Walletd exposes signer-tag limbs as fixed-width hex strings at the JSON boundary, while accepting legacy numeric limbs, so JavaScript clients cannot silently corrupt 64-bit policy material. `wallet/src/tx_builder.rs` exposes proof-backed value-lock, setup, approval, and final transaction builders for that shape. Value lock consumes a normal spendable native source note, pays an explicit fee, and creates a value note whose hidden `pk_auth` is derived from `(policy_root, final_intent_digest)`; the encrypted wallet stores the exact final plan beside that private opening so restarts do not strand locked value. Setup consumes a normal spendable native funding note, pays an explicit fee, creates the initial zero-value accumulator/control note for the same final intent digest, and returns native change when it fits the two-output transaction shape; approval consumes the current accumulator note plus a signer capability/value note, proves the signer note’s spend-derived tag is one active hidden policy tag, flips that hidden approved-slot bit, and creates the next accumulator note; final consumes only the value-locked note plus a threshold accumulator note for the same digest. Accumulator/control and value-lock note openings are stored locally because ordinary note decryption cannot recover arbitrary SmallWood `pk_auth` keys. Separate signer wallets exchange the private account descriptor and required local openings off-chain through explicit private import/export APIs; those payloads are not transaction fields. Sync reconciles such notes only against exact chain commitments already in the verified wallet commitment list and only when the stored opening recomputes that exact commitment. The older host opaque approval/final package APIs remain fail-closed. Public signer sets, thresholds, signer counts, signatures, policy roots, approval counts, approved slots, approval nullifiers, and authorization artifacts remain out of the transaction surface.
* `wallet/src/notes.rs` handles ML-KEM encapsulation plus ChaCha20-Poly1305 AEAD wrapping for both the note payload and memo. The shared secret is expanded with a domain-separated label (`wallet-aead`) plus the crypto suite so note payloads and memos use independent nonces/keys under `note-aead` and `memo-aead`, and suite-confusion fails authentication. Runtime validation hard-cuts ciphertext header acceptance to the active version (`v3`); mismatches are rejected fail-closed. The crypto, chain, and DA note-ciphertext parsers exact-consume their byte streams, reject unsupported wallet ciphertext versions, reject truncated payloads without panicking, reject nonzero fixed-container padding, reject noncanonical compact KEM lengths, and reject trailing bytes; that wire grammar is represented in Lean and checked against the production parsers with generated vectors. Lean now also proves that any byte-bounded accepted chain ciphertext projects to fixed DA bytes that reparse with the same public summary and carries the public ciphertext-hash binding as an explicit predicate over those DA bytes. The wallet decrypt admission order is represented in Lean as well: version, crypto-suite, and diversifier mismatches reject before crypto; accepted decrypt plus projected DA hash binding is packaged with production-profile facts for 32-byte KEM randomness, 32-byte AEAD keys, 12-byte AEAD nonces, 7-byte metadata AAD, distinct payload labels, and explicit residual assumptions for ML-KEM IND-CCA security, AEAD ciphertext security, wallet KDF domain separation, and encryption RNG freshness. Wrong-recipient/wrong-key, direct crypto AAD tampering, note/memo payload-label separation, and malleated KEM/note/memo payload behavior are regression-tested against production and modeled as explicit crypto-authentication assumptions rather than in-repo proofs of ML-KEM or AEAD security.
* `wallet/src/tx_builder.rs` exposes the transfer and burn output-batch count helpers used by native, stablecoin, burn, and consolidation planning. `Hegemon.Privacy.WalletOutputBatch` proves the accepted output count and primary-address change-output diversifier policy are determined by public shape, ignore private witness and wallet-local metadata seeds, and stay within the two-output public bound; generated vectors check those helpers and the shared production `change_output_address` helper without adding padding, dummy outputs, or hot-path proof work. Wallet-generated change outputs now use that cursor-independent primary-address helper instead of reserving cursor-derived internal addresses, so address-cursor advancement is not copied into newly built change ciphertext public summaries.
* `walletd/` is a sidecar daemon that opens a wallet store and exposes a versioned newline-delimited JSON protocol over stdin/stdout so GUI clients (like `hegemon-app`) can drive sync, send, and disclosure workflows without re-implementing cryptography. The protocol includes capability discovery plus structured error codes, and `walletd` enforces an exclusive lock file alongside the store to prevent concurrent access. For v0.9 strict operation, `walletd` defaults to self-contained unsigned submission (full proof/ciphertext bytes in the transfer extrinsic) so transactions remain portable across miners; DA/proof sidecar staging is opt-in (`HEGEMON_WALLET_DA_SIDECAR=1` / `HEGEMON_WALLET_PROOF_SIDECAR=1`) for deployments that explicitly coordinate sidecar availability.
* `wallet/src/viewing.rs` exposes `IncomingViewingKey`, `OutgoingViewingKey`, and `FullViewingKey`. Incoming keys decrypt ciphertexts and rebuild `NoteData`/`InputNoteWitness` objects for the transaction circuit, outgoing keys let wallets audit their own sent notes, and full viewing keys add spend-derived nullifier PRF material needed for spentness tracking without carrying `sk_spend`.
* `wallet/src/bin/wallet.rs` ships a CLI with the following flow:
  * `wallet generate --count N` prints a JSON export containing the root secret (hex), the first `N` addresses, and serialized viewing keys.
  * `wallet address --root <hex> --index <n>` derives additional diversified addresses on demand.
  * `wallet tx-craft ...` reads JSON inputs/recipients, creates redacted `TransactionWitness` JSON (omits `sk_spend`), and emits ML-KEM note ciphertexts for the recipients.
  * `wallet scan --ivk <path> --ledger <path>` decrypts ledger ciphertexts with an incoming viewing key and returns per-asset balances plus recovered note summaries.
  * `wallet node-sync`, `wallet node-daemon`, and `wallet node-send` are the live native node RPC flows; one-shot commands accept the native node's plaintext `http://` JSON-RPC endpoint while daemon/subscription mode still requires plaintext `ws://`. `wallet node-send` wraps the proof-backed shielded transfer in a kernel action and submits it through `hegemon_submitAction`.

Integration tests in `wallet/tests/cli.rs` exercise those CLI flows, so anyone can watch address derivation, note encryption, and viewing-key-based balance recovery stay compatible with the proving system.

Long-lived wallets rely on the native node JSON-RPC client (`wallet/src/node_rpc.rs`) and async sync engine (`wallet/src/async_sync.rs`) rather than ad-hoc scripts. One-shot status/sync/send flows can use plaintext HTTP or WebSocket RPC; subscription-backed daemon mode still needs plaintext WebSocket. The wallet rejects `https://` and `wss://` endpoints in the PQ-only release build; remote access belongs behind an external PQ-safe transport or host control plane. `AsyncWalletSyncEngine` pages through commitments/ciphertexts/nullifiers plus the latest block height, storing commitments inside the encrypted `WalletStore` so daemons can resume after crashes. The runbook in [runbooks/miner_wallet_quickstart.md](runbooks/miner_wallet_quickstart.md) walks through starting those daemons against two nodes.

Consolidation workflows retain sidecar-aware codecs for controlled historical experiments, but default to inline ciphertext and proof submission (`HEGEMON_WALLET_CONSOLIDATION_DA_SIDECAR=0`). Active native V2 rejects sidecar transfer actions, so setting either consolidation sidecar toggle is not a production route. Throughput remains bounded by the explicit per-round transaction/byte caps (`HEGEMON_WALLET_CONSOLIDATION_MAX_TXS_PER_BATCH`, `HEGEMON_WALLET_CONSOLIDATION_MAX_BATCH_BYTES`).

Ciphertext availability is policy-dependent: ciphertext bytes may be served from on-chain storage (inline) or from sidecar/DA stores. In the sidecar path, an external ciphertext stream can contain gaps (retention) or non-canonical ciphertexts (forks). Wallet sync therefore treats decrypted notes as valid only when their commitment can be found in the locally-synced commitment list; otherwise the note is skipped and sync continues. The native canonical wallet archive is stricter: `hegemon_walletCiphertexts` rejects gapped archive rows and archive indices at or above `leaf_count` before reporting observer-visible ciphertext metadata. The Lean archive boundary now proves accepted archive publication rows are contiguous from index `0` and every row is strictly below `leaf_count`, with generated vectors covering an accepted prefix below `leaf_count`, gaps, and leaf-count overruns. Nodes should report `walletNotes.next_index` as the maximum ciphertext index they can serve (which may exceed `leaf_count` for external sidecar streams), while `leaf_count` remains the canonical commitment tree size.

Third-party chain dashboards are no longer supported operator interfaces. Use the native JSON-RPC compatibility methods, walletd, Electron, and the runbook scripts for inspection and submission.

### 4.4 Retired disclosure proof boundary

The release wallet and walletd do not link a disclosure proof backend. They retain encrypted outgoing note-opening records for local accounting and allow those records to be listed or purged, but `payment-proof create|verify` and `disclosure.create|verify` fail closed and walletd advertises `capabilities.disclosure = false`. A future targeted payment-proof feature requires a separately reviewed proof implementation before the capability can be re-enabled.

## 5. Privacy & “store now, decrypt later”

Because we’re using only PQ primitives, the main “store-now-decrypt-later” concern is Shor-style compromise of legacy public-key assumptions, which this design removes:

* Hashes & symmetric: we dimension them (e.g. 256-bit hash output, 256-bit AEAD keys) conservatively so generic quantum search does not become the limiting factor. ([ISACA][4])
* Lattice schemes: we stick close to NIST’s strength categories for ML-KEM/ML-DSA. ([NIST][1])

Architecturally, we:

* Ensure that **address privacy** is not tied to any structure that might become classically invertible (no dlog; only KDFs).
* Use **one-time KEM keys** per transaction where helpful to add forward secrecy: sender can include ephemeral KEM pk in the ciphertext, so even compromise of recipient’s long-term `sk_enc` only reveals part of the past, not all.

The important property is that if a “Shor-class” machine appears, *nothing* trivially collapses, because there’s nothing ECC-based to break.

## 6. Upgradability & future-PQC break handling

We can hard-bake in lessons from the whole “quantum-recoverability” ZIP saga, but in a PQ setting:

1. **Versioned proofs & circuits**

   * Every transaction carries:

     * a circuit version ID,
     * a commitment to its statement in a version-agnostic way.
   * Recursion allows a new circuit to verify old proofs, so we can move from “Circuit v1” to “Circuit v2” without spinning up a new pool.
2. **Algorithm agility** for KEM/signatures:

   * Address versioning encodes a `crypto_suite` identifier for note encryption.
   * Wallets can rotate to, say, ML-KEM-v2 or a code-based KEM if lattices get scary; signatures continue to follow the protocol version bindings.
3. **Escape hatch**:

   * If some PQ primitive looks shaky, nodes can:

     * stop accepting new TXs using that primitive,
     * require users to “upgrade notes” via a special circuit that proves correct transfer into a new algorithm set.

So you get compartmentalized upgrades through *versioning & recursion* rather than parallel pools.

Concrete modules reflect the active split. `state/merkle` maintains the append-only commitment tree, each shielded action carries its canonical native SmallWood `tx_leaf`, and consensus verifies the ordered leaves directly. `circuits/block-recursion` is retained for historical decoding and verification only; new block construction does not depend on it, does not run a prove-ahead aggregate coordinator, and does not expose prepared-candidate artifact RPCs.

Consensus enforces version rollouts via `VersionSchedule`, a protocol-release structure that records which bindings are allowed at which heights. ZIP-style `VersionProposal`s (see `governance/VERSIONING.md`) specify activation heights, optional retirement heights, and any special upgrade circuits required to migrate notes from a deprecated primitive to a fresh one. The PoW network consults the schedule before accepting a block, so solo miners and pools can mix v1 and v2 proofs during a rollout without coordination beyond rebasing on the canonical chain. When an emergency primitive swap is required, operators follow the runbook in `runbooks/emergency_version_swap.md` to publish an activation proposal, enable the upgrade circuit, and shepherd users through note migrations before the retirement height lands; pools can track adoption by computing per-block version counts from transaction bindings.

## 7. What we explicitly **prune** from legacy shielded stacks

If we’re being ruthless:

1. **No transparent pool**

   * Every coin is shielded from genesis.
   * If you want transparency, you can reveal with a “view key” or build a public accounting layer on top, but the base protocol doesn’t do cleartext UTXOs.

2. **No multiple curve zoo**

   * No BN254, BLS12-381, Jubjub, Pallas, Vesta, etc.
   * All “algebra” is just over:

     * One STARK field for proofs,
     * Integer fields for value arithmetic,
     * Hash permutations for commitments.

3. **No trusted setups, no separate SNARK generations**

   * One transparent STARK family from day one.
   * Migration handled via recursion and circuit versions, not by creating new parallel pools.

4. **No ECC-based in-circuit commitments**

   * No Pedersen, no Sinsemilla.
   * Only hash-based commitments and Merkle proofs.

5. **Simplified key hierarchy**

   * One main shielded address type, with a clean, hash/KEM-based derivation for spend/view/enc keys.
   * No proliferation of key types and curves.

## 6. Monorepo structure, docs, and benchmarking

Implementation now follows an explicit monorepo layout so each subsystem’s tests, docs, and benchmarks stay synchronized:

- `crypto/` – Rust crate `synthetic-crypto` that implements ML-DSA/SLH-DSA signatures, ML-KEM, and the SHA-256/BLAKE3/Poseidon-style hashing used throughout this design. Changes here must update `docs/API_REFERENCE.md#crypto` plus the guardrails in `docs/THREAT_MODEL.md` that spell out the PQ security margins (≥128-bit post-Grover strength for all primitives).
- `circuits/transaction` and `circuits/block` contain the transaction proof system plus historical block-proof wrappers. The production benchmark is `compressed_level5_radix2_roundtrip_benchmark` in `transaction-circuit`; it constructs, proves, parses, and verifies the exact 64- and 128-lane SmallWood candidates in release mode and reports proof size plus elapsed proving and verification time. Section 2 must be updated in lockstep with those outputs.
- `consensus/` and `consensus/bench` – the Rust node logic enforces version bindings and PQ signatures for the protocol surfaces that require them, while active native V2 mining remains identity-free. The Go `netbench` simulator replays synthetic payloads sized to ML-DSA signatures plus STARK proofs; its output feeds the threat model’s DoS budgets because it reports achieved messages/second under PQ payload sizes.
- `wallet/` and `wallet/bench` – the CLI plus a Rust benchmark that derives keys, encrypts/decrypts notes, and computes nullifiers using the same derivations in §3–4. This ensures wallet UX changes keep Grover-aware 256-bit symmetric margins.
- `docs/` – authoritative contributor docs, threat models, and API references. The new files explicitly call out which paragraphs inside this DESIGN and `METHODS.md` must change together. Any interface change now requires edits in all three locations (code, DESIGN, docs) before CI will pass.

Continuous integration (see `.github/workflows/ci.yml`) mirrors this structure. Jobs cover:

1. Rust linting/tests across the workspace (crypto, circuits, consensus, wallet, state, protocol).
2. Targeted crypto tests to ensure ML-DSA/ML-KEM fixtures stay deterministic.
3. Circuit proof checks plus the release-mode SmallWood 64/128 candidate benchmark when proof geometry changes.
4. Wallet CLI/integration tests alongside the `wallet-bench` smoke test to exercise note encryption and nullifier derivations.
5. Go-based network simulator tests (`consensus/bench`) to keep PQ throughput budgets measurable.
6. A non-blocking `benchmarks` job that executes all smoke benchmarks and posts their JSON output in the build log for regression tracking.

These scaffolds exist to keep the design’s PQ security assumptions observable. Any change that alters signature sizes, hash widths, or witness semantics must update:

1. The relevant crate README (`crypto/README.md`, `circuits/README.md`, `consensus/README.md`, `wallet/README.md`).
2. The API entry in `docs/API_REFERENCE.md` and the guardrails in `docs/THREAT_MODEL.md`.
3. This section of DESIGN.md plus the operational instructions in `METHODS.md` so reviewers can verify code and documentation move together.

## 8. Security assurance program

- **Cryptanalysis & audits** – `docs/SECURITY_REVIEWS.md` defines how we commission lattice/hash reviews and third-party audits. Design-impacting findings must be mirrored in the sections above plus `METHODS.md`, and every mitigation PR links back to the finding ID logged there.
- **Formal verification** – TLA+ specs under `circuits/formal/` (transaction balance) and `consensus/spec/formal/` (PoW fork choice/finality), Lean kernels under `formal/lean`, and `config/formal-security-claims.json` are part of the release checklist. Any modification to witness layouts, balance tags, bridge message semantics, proof-artifact byte grammar, native codec/RPC/sync admission, supply-digest chain replay, or consensus phases must update the corresponding spec/vector/claim file and README.
- **Historical SmallWood statement, exact constraint map, wrapper, and accepted-block composition** - The retained V4 public statement is a 78-field verifier vector with version binding. Its V2/V3/V4 wrapper, exact-map, 16-mask, Poseidon, mutation, and conditional supply-composition evidence remains useful for regression and negative testing, but no V4 format is production-authorized. The later 893-byte V6/HGF6 statements, 128-limb projections, 79-call schedules, and SWV6 envelopes are also rejected historical fixtures and cannot name the successor. Fresh `HX448C02` instead uses a distinct 869-byte grammar with 125 scalar limbs and 109 M4 words, preserves the three live stablecoin authorities at 48 bytes, and explicitly rejects retired `HX448C01`. Its source-level M4 graph now emits the local non-hash, hash-link, and state-equality/lifecycle constraints, while four manifest/consensus authority predicates and aggregate scalar-to-M4 execution remain absent. The selected standard hash program and proof backend must be frozen before a fresh statement, action, rules, and envelope identity is allocated. Deployed PCS/IOP/Fiat--Shamir soundness, complete zero knowledge, composed QROM security, conventional-hash instantiation loss, and full compiler/native-node refinement remain explicit release blockers.
- **Continuous adversarial testing** – The `security-adversarial` CI job installs the pinned Lean toolchain manager before running the mandatory SmallWood Lean-vector conformance campaign, property-based tests for transaction validation, network handshakes, wallet address encoding, and the root-level adversarial flow in `tests/security_pipeline.rs`. `scripts/run_proving_redteam.sh` adds the Elan binary directory to `PATH` and fails before any campaign if `lake` is unavailable. Operators follow `runbooks/security_testing.md` when the job fails, capturing artifacts for auditors before re-running.

Together these loops ensure PQ parameter choices, circuit semantics, and miner logic stay observable and auditable as the system evolves.

## 9. Historical independent-proof runtime topology (not authorized)

The retained runtime was designed so new native blocks could carry an ordered chain of independently verified SmallWood transaction proofs. That same-byte transport invariant is still required for any successor, but the old V4/Poseidon proof family and every V6/HGF6 identity are not production authority. A cache may avoid repeated local work only after verification; it can never authorize an action or replace the proof.

The target transport invariants are:

- every shielded action carries one canonical native `tx_leaf`;
- new blocks carry no `proven_batch`, `block_artifact`, receipt root, commitment proof, or candidate action;
- candidate-artifact RPC submission fails closed;
- inline self-contained proof carriage is required;
- historical blocks with exactly one recursive artifact use the compatibility verifier;
- recursive proof kinds are absent from the active generic verifier registry.

This topology avoids the fixed historical recursive-block surcharge and aggregate proving delay. It does not activate shielded transfers, remove historical codecs, or reset chain history. Successor activation requires a coordinated fresh-identity protocol release and remains prohibited until every proof and security gate passes.

Known block-body locator admission resolves canonical membership and nonwinning stored branches from compact verified indexes plus an authenticated compact noncanonical fork summary. Repeated tiny locators therefore cannot make the Tokio protocol loop load or deserialize a maximum-size action body; only a plausible winning stored branch enters the bounded fair blocking import job, which still exact-compares the full persisted body before promotion or sync credit. A winning multi-block sync prefix is split at its last locally canonical ancestor and fully replayed before atomic publication; it does not need unsafe pre-persistence merely to make intermediate parent lookups succeed.

## 10. Historical V5 and rejected V6/Epsilon boundaries

The rejected SmallWood V5 experiment reserved `VersionBinding { circuit: 5, crypto: 4 }` and shielded action 7 without adding either to an active version schedule, proof-backend mapper, kernel manifest, wallet route, or native action router. It remains dormant historical evidence. V4/Gamma is also legacy/research-only rather than a production default. No V5/Delta or V4 byte string can be reinterpreted under a fresh successor identity.

The historical V5 candidate wire used an 80-byte `SWV5` header, 672 statement bytes, and one nonempty proof. Its 78-word public vector plus 48-byte balance tag and its caps remain parser fixtures only; they are not V6 grammar, byte measurements, or authorization.

The executable BLAKE2b-384 port is retained only as a negative architecture measurement and partial semantic oracle. Its 77-call schedule covers the old padded input/output metadata, 64 Merkle parents, balance, intent, stablecoin, and private-authorization surface but omits hashing the two full 2,147-byte ciphertext slots. Even that partial Boolean trace requires 164 compression blocks, 16,322,454 scalar constraints/witness bits, and 255,100 packed-64 rows before non-hash transaction logic. BLAKE2b-384 also supplies only the exact 128-bit generic quantum collision exponent with no composition margin, while the six-word digest slots cannot represent a wider output. It must not be routed into any production proof identity.

The V5 work established a useful transport invariant: an inline proof must absorb its complete identity, route, network, lengths, relation binding, and statement, and wallet-to-reorg carriage must preserve it byte-for-byte. Sidecars, aggregates, receipts, cached acceptance, and historical transaction-leaf substitutions remain invalid as authority. Any fresh successor inherits the invariant but not the V5 or V6 grammar.

The V5 boundary remains deliberately dormant. Its BLAKE2b-384 semantic scaffold is excluded from the current identity: the measured 255,100 packed hash rows are incompatible with the compact target, 384 bits leave no generic quantum-collision composition margin, and the partial schedule did not hash the full ciphertext slots.

Historical rejected V6/Epsilon descriptor evidence reserved `circuit = 6`, `suite = 5`, `family = 1`, `action = 8`, `backend = 2`, `profile = 2`, and `domain_set = 1`. Its `HGF6ST01` statement was grammar version 1 and exactly 893 bytes; three required zero bytes extended it to 896 bytes and 128 consecutive little-endian seven-byte limbs. `HGR6RM01` described two inputs, two outputs, all 16 activity masks, stablecoin, every authorization mode, 79 SHAKE256-448 invocations, and 124 Keccak-f[1600] permutations, including two fixed-width ciphertext hashes. Those are historical descriptor facts, not an active target. `HGF6ST01`, `HGF6ST02`, `HGF6HR02`, `HGR6RM02`, and `HGV6PB02` may never be reinterpreted for the fresh `HX448C02` diagnostic or any future production relation; retired `HX448C01` also may not be reused. A successor requires an entirely fresh identity after compiled evidence selects it.

The rejected `SWV6` parser fixture uses a 74-byte header, followed by the 893-byte statement, with proof offset 967. Its 512 KiB ceiling is a provisional parser-safety bound, not a measured cap or successor wire. No qualifying proof exists, `verified_max_proof_bytes` remains zero, and historical 87--118 KB SmallWood measurements plus the 1,344,828-byte M4 artifact are nonqualifying. The retained legacy radix-2 SmallWood engine profile also has an independently reproduced complete-ZK witness leak, while the current systematic BaseFold successor sketch exposes raw relation coordinates and is not zero knowledge. A qualifying backend needs a source-faithful masking construction, complete whole-view simulator including abort and Fiat--Shamir behavior, exact compiled relation, extraction, composed PCS/IOP/Fiat--Shamir/hash/grinding/union accounting above 128 post-quantum bits, deployed query/hash-loss bounds, formal and Rust-verifier refinement, retained mutation/restart/fresh-node artifacts, measured proof bytes, and a fresh source-bound release manifest. All capabilities and every HGF6/SWV6 route remain false until then.

### HGV8RP03 semantic adequacy boundary

The executable HGV8RP03 program and the transaction specification are separate objects. The
independent specification in `Poseidon2V8SemanticSpecification.lean` fixes the 120-word public
statement, the 721-word typed witness, two inputs, two outputs, all sixteen activity masks, all
three authorization modes, note commitments, nullifiers, the depth-32 Merkle path, action intent,
four balance slots, and the stablecoin transition. It also names the two public admission
conjuncts that are not arbitrary private packed-witness coordinates: the authenticated consensus
stablecoin context and each active output's exact 2,147 ciphertext bytes committed with
BLAKE2b-384.

`Poseidon2V8SemanticAdequacy.lean` states the universal source-level theorem over every canonical
public statement and every 43,904-word packed assignment accepted by the pinned program. Its
receipt cannot choose the semantic predicate. Instead it must supply an exact decoder and prove
five named obligations: canonical public structure, canonical witness shape, cryptographic links,
per-asset balance, and stablecoin transition. From those obligations Lean derives acceptance
soundness, invalid-opening rejection, typed-lowering completeness, and composition with consensus
context and ciphertext admission. The Rust receipt replays honest typed lowering through the
program-derived adapter and the existing exhaustive fixtures. The semantic target uses fixed
primitive symbols rather than receipt-selected functions, while separately recording that exact
source refinement for those symbols remains absent. This is executable regression evidence, not
the missing arbitrary-assignment or primitive-refinement proof. The checked-in Lean/Rust vector
therefore sets `exact_primitive_interpretation_refinement_proved=false`,
`universal_accepted_witness_soundness_proved=false`, and `production_authority=false`; V8 stays
fail closed until the primitive bridge, decoder, and all five universal obligations are discharged
and reviewed.
