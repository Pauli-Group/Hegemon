# Improve requested-range transport within existing bounds

This source-only proposal follows .agent/PLANS.md. It is not implementation or activation authority. All files in this directory are new private preparation artifacts; the frozen de7 candidate, running 408ca long qualification, production donors and credential supervisor remain unchanged.

## Purpose / Big Picture

Allow already requested canonical proof-bearing bodies between 256 KiB and the existing 8 MiB response budget to travel in the ordinary bounded response, rather than forcing each through a separate single-body request and ten-second egress window. The observable result is a mixed canonical range carrying contiguous medium-sized bodies in one existing Response message, while unsolicited announcements and genuinely larger bodies keep their current limits/carriers. No consensus, proof, source authority, action encoding, network identity or financial behavior changes are proposed.

## Surprises & Discoveries

The2-request admission limit is not the tight body-send bound: the full maximum reservation yields one positive send per peer window. Donor range loading in the retained examples is70–126ms, much smaller than the approximately10s single-body cadence. The read-only public RPC can export exact SCALE action chunks, but does not export the full historical native metadata needed to construct an exact P2P block. These facts change the shortest qualified route.

## RPC Export Alternative: Concrete Limitation

chain_getBlockActionsChunk (rpc.rs:1091–1135; node_impl.rs:12511–12585) exports exact canonical SCALE Vec<Vec<u8>> in1MiB chunks with total length/hash, tx_count, root, height, parent and before/after canonicality checks. The existing public helper verifies bound chunks, hashes, lengths and canonical decoding. This is appropriate for a bounded canonical public ACTION-body export, but not sufficient for a complete native P2P metadata fixture.

chain_getHeader/header_json (rpc.rs:1808–1834) exports only a32-byte hashed view of the original48-byte state_root and omits historical supply_digest/work_hash/timestamp fields. hegemon_blockTimestamps can recover timestamps in ranges<=4096 (rpc.rs:1410–1434), and hegemon_latestBlock exposes raw state/supply only for the current tip (node_impl.rs:12952+); neither supplies all historical raw state roots. state_getStorage returnsnull (rpc.rs:693–695). pow_header_json would expose more fields but is reachable through bridge witness export, which rejects unconditionally for current nativeV3 (rpc.rs:1467–1479). No block-import RPC is exposed. Do not default, invert a hashed state root, activate bridge export or inject unverified sled rows.

A public full-body donor built only from the currently exposed old-node RPC therefore needs an additional independently specified/qualified metadata export or a full state reconstruction/import tool. It is not the minimal same-binary route. A future actual collector must retain local-only actual transaction IDs and raw payloads, fix H14460 before collection, bind both approved donors' canonical anchor where available, recheck canonical hashes, stream regular create-only bounded files, hash exact bytes and reject reorgs/length overflow. With H=14460 and maximum64MiBaction bytes/block, the conservative aggregate is about904GiB, far above current20GiBheadroom; do not guess a safe export cap from the short fixture. Preflight actual lengths and stop before a reviewed cap/reserve. At least ~3H public RPC calls plus body chunks are needed for a naive per-block hash/header/body export, and each chunk revalidates/encodes its block body server-side; a bounded low-concurrency collector is necessary to avoid harming the donor. No collector/export was created or executed here.
