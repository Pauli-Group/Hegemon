This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds. It is maintained in accordance with `.agent/PLANS.md` and is part of the series described in `.agent/SWAP_SERIES_EXECPLAN.md` (plan 3 of 8). ## Purpose / Big Picture

Today the hosted page (a Cloudflare Worker serving the files in `swap-ui/`) can only read public testnets and send a few manual Sepolia transactions. Every other action in a swap (Sepolia claim, all Bitcoin testnet4 actions, all Cardano preview actions) needs a command-line script or the loopback "companion" (`scripts/local_swap_companion.py`) that holds private keys on the user's machine. A person with only a browser wallet cannot finish a swap, and nothing in the browser can read the counterparty's claim to learn the preimage (the secret whose SHA-256 is the hashlock).

After this plan a user can, from the hosted page alone: claim a Sepolia escrow from an encrypted preimage backup; fund, claim and refund a Cardano preview escrow through a CIP-30 wallet (the standard browser API Cardano wallets expose under `window.cardano`); fund, claim and refund a Bitcoin testnet4 escrow by building a PSBT (a partially signed Bitcoin transaction, the standard unsigned-transaction exchange format) that a PSBT-capable wallet or tool signs; have the page find the counterparty's preimage on any of the three chains and save it into the encrypted backup; and follow a guided view that shows, for the current swap, which step the swap state machine is in, what the timelock policy says right now, and what is safe to do next. Hegemon remains a clearly labelled "unavailable on public testnet" leg here; P6 and P8 add it.

Terms used in this plan. An HTLC (hash-time-locked contract) is an escrow that pays a claimant who presents the hashlock's preimage before a deadline and otherwise lets the funder (the refundee) take the money back afterwards. The "long leg" is funded first by the initiator and expires later; the "short leg" is funded by the responder and expires earlier. The initiator claims the short leg (revealing the preimage) and the responder reads it and claims the long leg. The "engine" is the Python state machine from P2 (`scripts/swap_engine/engine.py`); "the policy" is the P1 timelock policy (`swap-ui/timelock-policy.mjs`, `scripts/swap_engine/timelock_policy.py`, configured by `config/swap/chain-timing.json`). An "observer" reads a chain to find the transaction that spent an escrow and the preimage in it. "Qualification" means exercising the page with software that is not our own test double. A "read proxy" is a Worker route that fetches public chain data on the page's behalf, because the page's Content-Security-Policy allows network connections only to its own origin.

This is testnet software. It does not make real-funds swaps safe, and Outcomes states exactly which wallets were and were not qualified.

## Surprises & Discoveries

Cardano: a Plutus transaction's validity upper bound must lie inside the ledger's time horizon (about seven hours on preview), so a claim's `ttl` is clamped to `CLAIM_VALIDITY_SLOTS = 3600` slots past the ledger tip, and the Python adapter's preview `validity_slots` is 3600 for the same reason (the private cluster profile uses 20 because its ledger translates slots only about 30 ahead). The execution budget that was budgeted from unit assumptions (10 million memory, 10 billion steps) was far above what the validator needs; the pinned fixed budget is 250000 memory and 100000000 steps. The page's fee check recomputes the minimum fee from the protocol parameters (size fee including the expected witness bytes plus the execution-unit fee) and refuses a fee below it by more than a small byte margin or above it by more than a fixed slack, instead of trusting the builder. Koios answers an empty `tx_info` or `tx_cbor` for a confirmed transaction while a backend lags, which the observer and Worker treat as pending. Preprod and preview share network id 0, so the page proves "preview" only by asking the Worker whether the wallet's UTxOs exist on preview. Wrangler is not installed on this host, so the Worker could only be tested through its unit adapter, a Node host (the qualification harness) and the Python and Playwright tests; deployment is the operator's step. For Bitcoin, embit's `PSBT.serialize` derives the transaction from `psbt.outputs`, so the regtest tamper test had to mutate `psbt.outputs`; a fund PSBT signed with an unexpected sighash flag was accepted by the first version of the checker and is now refused (requested `sighashType` undefined or ALL, and every partial or final ECDSA signature flagged ALL). During qualification: Node's default 250 ms per-address connect attempt made the Worker's provider reads fail with ETIMEDOUT from this host (fixed in the harness by `net.setDefaultAutoSelectFamilyAttemptTimeout(5000)`; Cloudflare's runtime is not affected); the Worker's `/sepolia/escrow-events` failed on a real escrow because it asked publicnode for logs from block 0 and publicnode caps ranges at 50000 blocks (fixed with bounded windows and a `scanned_from` field); and one harness mistake filled the claim form with a different expiry than the deployed escrow, which the page correctly refused as a bytecode mismatch (the message does not tell the user which term differed). `swap-service/browser.test.mjs` still passes and then aborts with a Node internal assertion at exit on Node 24.22.2; this predates this plan.

## Decision Log

- Decision: the page does not port the signing engine. It ports only the pure functions `decide` and `explain` (for display) and `plan_with_margin` (for suggested expiries). Python stays the source of truth: `scripts/swap_engine/ui_vectors.py` generates `config/swap/flow-vectors.json` from `engine.TRANSITIONS`, the decision tests and the planner; the JS module is tested against it and a Python test fails if the checked-in file is stale. Rationale: P2 revision; two implementations that are tested against the same vectors cannot silently drift. Date: 2026-11-06.
- Decision: the page writes nothing the engine would treat as a signed action. It shows the CLI commands (`advance`, `receive`, `resolve`) and the engine's own `explain` text for a state, and the wallet actions it performs are its own, journaled in the browser action journal before each wallet request. Rationale: P2 revision; the engine's inflight bookkeeping is journal-based per participant and a second writer would break it.
- Decision: the page's swap terms are the engine's terms JSON (version 1, `hashlock`, `legs.long|short` with `chain`, `amount`, `refundee`, `claimant`, `expiry`), and the swap id is the first 16 hex characters of the SHA-256 of the canonical terms (sorted keys, no spaces). The page recomputes the id and rejects a mismatch. Escrow references are `{txid}` for Ethereum and `{txid, vout:0}` for Bitcoin and Cardano and are untrusted until a verifier confirms them against the terms.

- Decision: third-party browser code is vendored, not fetched. The sources are `swap-service/vendor-src/` (deliberately outside `swap-ui/`, because the Worker serves every file under `swap-ui/` and `node_modules` must never be uploaded): an exact-pinned `package.json`, its `package-lock.json`, two entry files and `build.mjs`, which uses esbuild to write `swap-ui/vendor/btc-signer.mjs`, `swap-ui/vendor/hash.mjs`, `MANIFEST.json` (dependency versions and npm integrity hashes) and `SHA256SUMS`. `node build.mjs --check` fails if the committed bundles differ from a fresh build, and `swap-ui/vendor.test.mjs` fails if a bundle's SHA-256, a version pin or an integrity hash drifts. Pins: `@scure/btc-signer` 2.4.1, `@noble/hashes` 2.4.0, `@noble/curves` 2.4.0, `@scure/base` 2.4.0 (esbuild 0.25.12 is the build tool and is not shipped). Rationale: the page has no build step and a strict Content-Security-Policy; a committed, checksummed bundle is what P5 can integrity-pin. Date: 2026-11-06.
- Decision: Bitcoin uses `@scure/btc-signer` (pure JavaScript from the audited noble/scure family) to build, parse and finalize PSBTs. Rationale: it supports P2WSH inputs with a witness script, custom final witnesses and the testnet bech32 prefix `tb` (testnet4 uses the same prefix as testnet3), with no WASM and no Buffer polyfills. Date: 2026-11-06.
- Decision: Cardano uses a purpose-built builder (`swap-ui/cardano-tx.mjs`) for exactly three transaction shapes (fund, claim, refund) instead of a WASM serialization library, with `blake2b`, `ed25519` and `bech32` from the vendored `hash.mjs`. Rationale: the plan calls for "a pinned, vetted library", and the candidates are `@anastasia-labs/cardano-multiplatform-lib-browser` 6.2.0-2 and `@emurgo/cardano-serialization-lib-browser` 17.0.0, each about 4 MB unpacked, loaded as WASM, which requires adding `'wasm-unsafe-eval'` to the page's Content-Security-Policy (weakening the policy for the whole page) and brings a general transaction API whose surface we would have to audit although we need three fixed shapes. A narrow builder is small enough to read in one sitting, and its output is not trusted on its own authority: it is checked (a) by an independent decoder that re-reads the exact bytes before they reach the wallet, (b) differentially against `cardano-cli`-built transactions for the same inputs, and (c) by a real ledger and validator on the local Cardano cluster and on preview. This deviates from the plan's wording (library) and is recorded as such in Outcomes. Date: 2026-11-06.
- Decision: Cardano script execution budgets are a fixed budget, measured on the local cluster and rounded up with margin (value recorded in Artifacts and Notes), applied to the redeemer; fee and collateral are computed from it and capped. An evaluation endpoint is not used: Koios has none, Ogmios is not installed on this host, and Blockfrost and Maestro need API keys, which the hosted page cannot hold. Rationale: the validator is a hash comparison, a signer check and a validity-interval check, so its cost is nearly constant and a fixed budget is sound; the cost of being wrong is a failed phase-2 validation that forfeits only the collateral input.

## Outcomes & Retrospective

The hosted page can now claim a Sepolia escrow from an encrypted backup, fund, claim and refund on Cardano through CIP-30 with the transaction decoded and compared to the terms before signing, fund, claim and refund on Bitcoin through PSBT export and import, observe a counterparty's revealed preimage on all three chains through Worker read proxies, and show a read-only guided view that applies the P1 policy verdict and the P2 decision rules. Evidence: 133 JavaScript unit tests, Playwright suites with mocked wallets, real-software local tests (a private Cardano cluster and bitcoind regtest) and a qualification run on Sepolia, Cardano preview and Bitcoin testnet4 whose transaction ids are in `PUBLIC_TESTNET_RESULTS.md` and which I re-read independently on each chain.

What was not achieved: no browser-extension wallet was used (stand-ins signed with the same key material), the Worker routes were hosted in Node and not deployed, declined-signature and stale-head cases ran only against mocks, the guided view was never run against a live engine swap, the Bitcoin claim and refund came from two runs and not one, and Hegemon is labelled unavailable. Lessons: a real-chain run found a Worker bug (publicnode caps `eth_getLogs` ranges) that every mocked test had missed; Koios returns partial `tx_info` while lagging; Node's 250 ms connect-attempt default breaks provider reads here; error text for escrow mismatches should name the differing term.

A test fails if `swap-ui/chain-timing.json` differs from `config/swap/chain-timing.json`.

Contracts. Ethereum: `contracts/ethereum/HegemonHTLC.sol` (`claim(bytes32 preimage)` selector `bd66528a`, `refund()` `590e1ae3`, event `Claimed(bytes32 preimage, address indexed recipient, uint256 amount)`). Bitcoin: the P2WSH script above; a claim witness is `[signature, preimage, 0x01, script]`, a refund witness is `[signature, empty, script]` with transaction locktime equal to the refund height and input sequence 0xfffffffe. Cardano: `contracts/cardano/validators/htlc.ak` (PlutusV3, script address `addr_test1wqmp4fms223lnjljntag8vk9frl0l8pygsp2pt75tv2llsgmwwmyv`; inline datum constructor 0 with fields hashlock (32 bytes), claimant key hash (28), refundee key hash (28), expiry in milliseconds; claim redeemer constructor 0 with the preimage, refund redeemer constructor 1; the claim must finish before the expiry and the refund starts at it; the spender must be a required signer).

Engine schema (P2). Terms are described in the Decision Log. States for the initiator: `terms_saved`, `long_fund_submitted`, `long_funded`, `short_verified`, `short_claim_submitted`, `done`, `refund_submitted`, `refunded`; for the responder: `terms_saved`, `long_verified`, `short_fund_submitted`, `short_funded`, `preimage_known`, `long_claim_submitted`, `done`, `refund_submitted`, `refunded`; terminal `aborted` and `failed`. `needs_human` and `inflight` are flags on the record, not states. The decision function `engine.decide(record, terms, obs, config, now)` returns `move`, `act`, `wait`, `abort`, `halt` or `terminal`. An observation is `{now, heads:{long,short}, legs:{long,short}, errors, preimage_available}` and a leg observation has `found, verified, problem, confirmations, spent (null|claimed|refunded), spend_confirmations, spend_txid, preimage`.

Provider behaviour the page must respect: Koios answers `[]` for confirmed transactions (`tx_info`, `tx_cbor`) while a backend lags, so an empty answer for a confirmed transaction means "pending", never "no preimage"; the public Ethereum RPC has no mempool, can return a null receipt for a mined transaction and prunes old logs (Blockscout is the fallback); Blockstream's outspend endpoint shows mempool spends; Koios has no script-evaluation endpoint.

Wallet addresses for tests live under `~/.local/share/hegemon-testnet-wallets-20261104/testnet-wallets/{alice,bob}`; their private keys are never read by this plan's code except by the qualification harness, which takes file paths from the environment and never logs key material. Never print or commit anything under `~/.hegemon-private`.

## Plan of Work

Milestone 1 chooses the libraries. The page has no build step and a strict Content-Security-Policy, so third-party code must be vendored as pinned, checksummed static files under `swap-ui/vendor/`, produced by a reproducible script from a locked `package.json` in `swap-ui/vendor-src/`. Bitcoin uses `@scure/btc-signer` (zero-WASM, audited noble/scure family) bundled to one ES module. Cardano: the options are a WASM serialization library (CML or CSL, about 4 MB unpacked, needing `'wasm-unsafe-eval'` in the Content-Security-Policy) or a purpose-built builder for the three transaction shapes this system needs. The decision and its evidence are recorded in the Decision Log. The Cardano script execution budget is a fixed budget measured on the local cluster and capped by the protocol limit, with fee and collateral computed from it; an evaluate-capable provider is documented as unavailable (needs an API key or a node we do not host).

Milestone 2 adds `swap-ui/swap-flow.mjs` (terms validation, swap id, `decide`, `explain`, `planWithMargin`) and `scripts/swap_engine/ui_vectors.py` that writes `config/swap/flow-vectors.json`. `swap-ui/swap-flow.test.mjs` runs the vectors; `scripts/swap_engine/test_ui_vectors.py` regenerates and compares.

Milestone 3 adds Sepolia claim: `claimSepoliaEscrow` in `swap-ui/sepolia-actions.mjs`, with the same checks as the local claim (pinned runtime, hashlock matches backup, funded and unspent at a confirmed snapshot and at the head, simulation succeeds), the policy checks (a claim cutoff from `legWindow` and `actionSeconds` for the leg being claimed, and, when the claimant is the initiator, the engine's rule that the other leg is still compliant), and the existing warning that the preimage reaches the wallet before the user approves.

Milestone 4 adds `swap-ui/cardano-tx.mjs` (CBOR codec, builder, and an independent decoder/checker that reads the exact bytes handed to the wallet) and `swap-ui/cardano-wallet.mjs` (CIP-30 flows: network check, UTxO selection, build, decode and compare to terms, journal, `signTx`, assemble, `submitTx`). Differential tests compare our bytes with `cardano-cli`-built transactions and a local-cluster run proves the ledger and validator accept them.

Milestone 5 adds `swap-ui/bitcoin-psbt.mjs` (funding, claim and refund PSBTs, an independent checker, and finalization of the custom witness) and the export/import UI path.

Milestone 6 adds `swap-ui/observers.mjs`, the Worker routes it needs, and the save-to-backup step.

Milestone 7 adds `swap-ui/guided.mjs` and a "Guided swap" section.

Milestones 8 to 10 test, qualify and document.

## Idempotence and Recovery

Vendor builds are deterministic and checked against `swap-ui/vendor/SHA256SUMS`. A wallet request is preceded by an action-journal record; after a lost response the page reports the action as uncertain and offers no automatic retry. Nothing here writes engine state.
